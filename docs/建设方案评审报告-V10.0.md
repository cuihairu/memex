## 执行摘要

本报告回答三个问题：**在内网隔离环境下能否用现成开源软件替代当前的局域网沟通工具；如果不能，应当如何自建；以及建设到什么程度、分几步走。**

结论是：**现成开源软件无法满足，采用纯自研方案；功能范围按四期规划推进，第一期交付沟通与文件共享本体，第二期交付办公能力，第三期交付 AI 能力，第四期视条件推进会议与协同文档。**

| 结论项 | 内容 |
| --- | --- |
| 技术路线 | 纯自研，不采用开源软件二次开发 |
| 许可纪律 | 不集成 AGPL／SSPL 等强传染性许可组件；开源组件仅以部署调用或宽松许可链接方式引入，交付时提交组件清单 |

| 客户端形态 | 单一安装包内含两套引擎：未登录时为零配置直连态，登录后为服务端协作态 |
| 归档边界 | 协作态消息全量落服务端；直连态消息仅存本机（符合该形态的固有属性） |

本版（V10.0）只有一处调整：**确定系统的英文名与代号为 Memex**，并在第五章新增第六节「系统标识与命名规范」，把命名依据、标识清单与一处需要避开的表述口径固定下来。命名在本方案中不是装饰性事项——它必须同时满足四条约束：不与已评估并排除的开源项目同名；不与商用办公通讯产品近似；不暗示私密或监控；可直接作为标识符使用。这四条约束是前几版讨论的沉淀，写入报告后不再需要临时解释。

以下三项由上一版（V9.0）确立，本版继续沿用，均围绕「媒体能力的技术底座与许可边界」这一主题。

**其一，明确 WebRTC 为全系统媒体传输底座（第四章新增第十节）。** 远程协助的画面流、音视频会议的媒体流与屏幕共享共用同一条通道，统一以 WebRTC 为标准传输底座，不自研传输层。该节同时划清 WebRTC 的能力边界——**它是管道，不含管道两端的能力**：屏幕采集、输入注入、授权确认、多人转发（SFU）与操作留痕均不在其内，仍须自行实现或另行集成。由此也界定了远程协助 3–4 人周工作量的确切范围。

**其二，确立“组件级许可纪律”，并据此修正远程协助的选型论据（第三章新增第四节、第二章第四节）。** 本方案排除的是**强传染性许可（AGPL／SSPL）组件的集成**，而非一切开源组件——调用模型、部署媒体服务器、链接宽松许可的协议库均在允许之列，第三方组件清单随交付一并提交。据此重写了远程协助一项的论证：除 RustDesk 因 AGPL 被排除外，**另有 MeshCentral、Guacamole、FreeRDP 三个 Apache-2.0 方案，它们被排除的原因不是许可证，而是与本方案的授权交互及可见性要求不匹配**。

**其三，客户端技术选型增加“媒体能力”评估维度（第五章第三节）。** 原选型仅比较开发效率、打包体积与国产系统适配，未考虑 WebRTC 在目标环境中的可用性。核查发现**主流发行版打包的 WebKitGTK 默认不编译 WebRTC，Tauri 路线在国产 Linux 终端上无法建立媒体连接**，而国产系统是本项目的必覆盖目标。据此调整了三个候选方案的评估结论，并同步补入技术风险表与第一期验收标准。

**以下两项由上一版（V8.0）确立，本版继续沿用。**

**其一，明确"留痕优先"原则，并列出明确不提供的功能（第一章、第二章）。** 本次澄清了一处曾被误读的表述：方案中提到的"密聊（阅后即焚）"，指的是**当前局域网工具已有的功能特征**，引用它是为了说明推行阶段的员工预期落差，**不是本方案要建设的能力**。据此在需求清单与功能盘点两处明确列出不提供的四类功能：密聊与阅后即焚；撤回时同步抹除服务端归档；终端侧单方删除归档记录；面向使用者的留痕开关。**连接服务端的目的就是留痕，任何可由发送方自行消除留痕的功能，都与该目的互斥。** 这一条同时反向解释了直连态"不经服务器、不留档"必须作为形态的固有属性保留，而不是一个可以按需调用的隐藏模式。

**其二，直连态的适用范围收敛为本网段（第八章）。** 免登录直连态定位为**本网段内的临时、就近使用**——临时来客、临时借用一台机器、同一办公区域内即时问答这类场景，装完即用、用完即走。据此明确一条边界：**直连态不追求跨网段自动发现，也不为其安排任何网络侧改造**；跨网段与跨地域的通信需求一律由协作态承接。上一版提出的"本地服务器兼作发现节点"备选方案随之删除，相关的网络侧前置条件与决策事项一并简化。调整之后，直连态的可用范围完全由其固有性质决定（UDP 广播不出网段），**不需要任何外部协调即可落地**。

**以下两项由 V6.0 版确立，本版继续沿用。**

**其一，沟通体验类功能补入清单与分期（第二章）。** 补充截图与标注、表情包、常用联系人、直属上级与汇报关系、通讯录可见性、办公室位置图、远程协助共七项，按依赖关系分别归入第一期与第二期，并给出各自实现要点与工作量。其中远程协助与办公室位置图涉及权限管控与场所信息安全，已在第二章与第九章专门说明。

**其二，AI 模型接入层明确为可插拔的模型网关设计（第六章第五节）。** 统一采用 OpenAI 兼容协议，本地模型与外部 API 端点均可注册；但归档数据只允许送本地模型，外部端点默认禁用、需显式注册并留存审计记录。该设计使第三期的软件工程部分可以在硬件到位前先行完成，把硬件采购周期与开发进度解耦。

**以下三项由更早版本确立，本版继续沿用。**

**其一，技术路线由"改造开源项目或自研"收敛为"纯自研"。** 上一版仍将改造成熟开源项目列为可选路径；本次确认不采用开源二次开发，理由是开源即时通讯软件普遍采用强传染性许可证（AGPL-3.0），改造后对外提供服务需公开自有代码，且在服务端中心化的客户端内嵌入免服务端子系统存在架构冲突，改造工作量并不低于自研。第三章详述。

**其二，功能范围由"三项核心功能"扩展为"对标企业微信"。** 这一目标涵盖沟通、办公、协同、会议四个领域，各领域的开发量差异极大。第二章将企业微信的功能拆解为可评估的清单，按依赖关系与开发量排出四期，并明确标出其中两项建议不自研。**这是上一版最重要的内容——它把"向企业微信看齐"这个目标转化为可以立项、可以验收、可以控制风险的实施路径。**

**其三，账号模型由"身份与本机硬件绑定"修正为"多端登录管控"。** 上一版将需求理解为账号锁死在一台终端上；本次明确为：账号可在不同电脑登录（换机可用），但桌面端同一账号只允许一个在线，重复登录时前一个客户端被下线，每次登录均标注设备类型并留存记录。第四章第五节详述。

其九，模型网关是否允许注册外部 API 端点（建议默认不允许；如允许，须限于非归档数据并全程留审计）；其十，是否启动 GPU 硬件采购评估；其十一，是否配合实施网络层准入控制；其十二，远程协助的开放范围（建议仅面向 IT 运维人员，且需被控方显式授权、全程留痕）；其十三，办公室位置图的覆盖范围与可见权限（建议按园区与楼层限定可见范围）；其十四，通讯录可见性策略（建议默认全员可见，高管的联系方式等信息按需隐藏）；其十五，直属上级数据的来源（建议先由管理后台手工维护并支持批量导入）。

## 一、项目背景与需求分析

本章先说明工具选型所处的环境约束，再将需求拆解为可验收的条目，说明需求在多轮沟通中的收敛过程，最后确立贯穿全案的设计原则。

### （一）项目背景

当前内网办公环境依赖局域网即时通讯工具完成日常沟通与文件传递。该环境具备三个特征。

**网络与公网物理隔离。** 内网不具备访问互联网的条件，任何依赖外部服务器、外部账号或联网校验的商用通讯软件均无法使用。这一约束同时决定了后续 AI 能力的实现方式——模型必须部署在内网。

**终端操作系统混用。** 终端在 Windows 与国产 Linux（统信 UOS、麒麟）之间混用，客户端必须同时覆盖两类平台，且国产系统上的适配问题通常多于 Windows。

**现有工具功能不足。** 当前使用的内网通讯工具在沟通与文件传递上可用，但缺少组织架构、消息检索、办公协同等能力，使用体验明显弱于企业微信、飞书一类产品。这正是本次提出"对标企业微信"的现实动因。

由此确立本次建设的约束条件：**功能上向商用产品看齐，实现上必须完全自主可控、完全内网运行。**

### （二）需求清单

**表 3　需求清单与验收口径**

| 编号 | 需求 | 优先级 | 验收口径 |
| --- | --- | --- | --- |

| R5 | 两种模式集成于同一客户端 | 必须 | 单一安装包；未登录为直连形态，填写服务器地址并登录后切换为协作形态；切换不丢本地历史 |

| R7 | 消息归档范围须可标识 | 必须 | 跨态会话（一方未登录）在界面上明确标注不留档；归档起点可追溯 |
| R8 | 支持国产操作系统 | 重要 | 至少覆盖统信 UOS 与麒麟 Linux |
| R9 | 跨网段与多地域通信、大文件传输 | 重要 | 跨网段与跨地域通信由协作态承接：多地域经专线接入同一服务端、跨域消息可达；直连态限于本网段、不作跨网段要求；支持整目录发送与断点续传 |
| R10 | 功能对标企业微信 | 重要 | 按第二期分期清单逐项验收，不要求一次性达成 |
| R11 | 内网 AI 能力 | 计划 | 群内智能助手、会议纪要生成、需求整理；模型内网部署，数据不出内网 |
| R12 | 服务端高可用 | 重要 | 服务端故障时直连态仍可通信；运维侧具备备份与恢复预案 |
| R13 | 沟通体验（截图、表情、常用联系人） | 重要 | 内置截图与标注后可直接发送；支持自定义表情包导入；常用联系人可置顶与快速查找 |
| R14 | 组织架构含汇报关系与通讯录权限 | 重要 | 成员资料可查看直属上级；支持按部门设置通讯录可见范围；高管联系方式等信息可单独隐藏 |
| R15 | 办公室位置图 | 计划 | 可查看楼层平面图并定位同事工位；搜索姓名后图上高亮；按园区与楼层限定可见范围 |
| R16 | 远程协助 | 计划 | 可请求远程查看或控制同事终端；须被控方显式授权、过程对被控方持续可见、全程留痕 |

**需求清单之外，以下功能明确不提供。** 需要单列这一说明，是因为其中几项在商用即时通讯产品中普遍存在、且颇受使用者欢迎，容易被误当作功能清单的遗漏。本方案不提供它们并非能力不足，而是目的使然——**连接服务端的唯一目的就是留痕，凡"使发送方得以自行消除留痕"的功能，与该目的直接冲突。**

第一，**密聊与阅后即焚。** 不存在任何"发送后自动消失""服务端不保存"的会话形态。协作态的一切会话一律归档，用户无法选择某条会话不留痕。

第二，**撤回并抹除归档。** 撤回功能保留，但其作用范围仅限客户端显示层——服务端完整保留原始消息内容与发送时间，同时额外记录撤回动作本身（谁、何时、撤回了哪条）。**撤回是"我不想让你再看到"，不是"系统不再留存"。**

第三，**终端侧单方删除归档。** 员工可以清理本机缓存，但该操作不影响服务端记录；客户端界面上必须明确区分"本地缓存"与"云端归档"，避免员工误以为清空本地即等于删除记录。

第四，**面向使用者的留痕开关。** 留档策略只能由管理侧按部门统一下发，客户端不向使用者提供任何关闭留痕的选项。

### （三）需求演进与本版收敛

本项目需求经多轮沟通逐步收敛，演进过程本身对理解方案形态有必要，故一并说明。

**最初需求为"彻底取消账号，身份完全跟随硬件"。** 此路径与"聊天记录集中留存"存在逻辑互斥：没有账号，服务端无法判定消息归属，也就无法建立可检索的记录。

**随后调整为"默认免登录可用，账号为可选增强"。** 账号体系得以保留，但方案被设计为单通道——未登录用户也须经由服务端，以保证留档口径统一。此路径的问题是："免登录"不再等于"免服务器"，而用户对免登录形态的预期是"像飞秋一样不填地址、不架服务器"。

**本版最终确认为"双引擎形态"，并逐项澄清了四项边界。**

第一，**未登录即零配置直连**。不填服务器、不连服务器、UDP 广播自动发现、点对点直达——这才是用户所预期的"飞秋形态"。

第二，**登录即接入服务端协作**。填写服务器地址后，消息进入服务端归档，获得组织架构、云端历史、检索等能力。

第三，**两种形态同装于一个客户端**。用户明确要求二者集成，而非两个软件。

第四，**账号支持换机登录**。用户明确"以后其他电脑可以登录"，并给出管控要求：不同端可并存，同为电脑端则互踢，保留一个在线，登录须标注设备类型。

第五，**沟通体验与组织信息类能力补齐**。用户对照现有局域网工具与企业微信，补充提出六类能力：远程协助、截图、表情包、常用联系人、登录后可查看组织架构与上层领导、办公室位置图，并明确这些能力应与前述四项一并规划，而非留待后续。本版将其全部纳入分期；同时由"通讯录中可见哪些人、哪些字段"派生出通讯录可见性控制这一衍生要求，一并纳入。

第六，**直连态的适用范围收敛为本网段**。免登录直连态依赖 UDP 广播发现，而广播不出网段——这是网络设备的固有行为，非配置问题。用户据此明确其定位为**本网段内的临时、就近使用**，不追求跨网段自动发现，也不为其安排任何网络侧改造；需要跨网段或跨地域沟通时，登录协作态即可。这一确认使直连态的边界由其自然属性决定，不再是一项需要外部配合、需要排期的工程任务。

第七，**留痕为唯一目的，不接受可规避留痕的功能**。用户明确"连接服务器就是为了留痕"。据此确立一项排除性要求：凡是让消息发送方得以自行消除留痕的功能——密聊、阅后即焚、撤回即删除、终端侧单方删除归档——一律不纳入本方案。这一条同时厘清了另一处容易被混淆的表述：本方案并非在"保留一些旧工具的不留痕特性"，而是恰好相反——**直连态的不留痕是其形态的固有属性，协作态的留痕是建设目的本身；前者不是可以按需调用的隐藏功能，后者不容任何技术手段豁免。**

### （四）设计原则

由上述需求确认四条贯穿全案的设计原则。

**原则一，双引擎并行。** 客户端内并存两套通信引擎，各自完整、各走各的链路。二者不共享通信状态，只共享本地数据层。这一条消除了"两套通道状态同步"这一本类系统最集中的缺陷来源。**两套引擎的适用范围也由此自然分开：直连态依赖 UDP 广播，其适用范围即本网段、定位为临时就近使用；跨网段与跨地域一律走协作态。**

**原则二，留档边界由形态决定。** 协作态消息全量落库；直连态消息只存本机。管理侧看到的归档记录，其边界就是"该员工登录之后产生的内容"——边界稳定、可预期、可向员工说明。**这是一个必须如实告知的边界，而非需要通过技术手段弥合的缺陷。** 同时须确立一条硬约束：**归档一旦产生，即不可由消息发送方消除。** 撤回只改变客户端显示，不改变服务端记录；终端侧清理本地缓存不影响归档；系统不提供面向使用者的留痕开关。凡与这一条冲突的功能一律不建设——理由很简单，**连接服务端的目的就是留痕，若留痕可被发送方自行豁免，该目的即落空。**

**原则三，跨态互通须显式标识。** 已登录用户与未登录同事之间可以互通，但该链路不经服务端、无法归档。凡此类会话，界面必须显式标注不留档，并配套服务端可下发的策略开关，防止该通道被用于规避留存。

**原则四，可自研的才自研。** 音视频会议与协同文档属于独立技术领域，自研代价高、质量难以保证，应采用采购成熟产品或在允许范围内集成开源组件的方式解决，不纳入自研范围。这一原则是"对标企业微信"能够落地的前提。

**原则五，敏感能力默认收紧。** 远程协助、通讯录可见范围、办公场所图这三项，默认值一律取最保守的一档，由管理侧按需放开。这与"功能向商用产品看齐"并不矛盾——看齐的是能力，不是默认权限。远程协助默认不对普通员工开放，通讯录默认全员可见但支持例外收紧，场所图默认仅本人所在楼层可见。

### （四）六项体验功能的实现要点

本版补充的六项功能，开发难度差异很大，其中两项存在容易在立项阶段被低估的问题，故单列说明。

**截图与标注。** 客户端本地功能，实现路径成熟：截取屏幕、叠加涂鸦／箭头／马赛克／文字图层、确认后写入会话。**功能本身不难，难的是三处适配细节**：多显示器下的区域选择、高 DPI 缩放下的像素对齐、国产 Linux 下的取屏接口差异（X11 与 Wayland 方式不同，麒麟与统信各版本的默认会话类型并不一致，需逐一实测）。工作量约 0.5–1 人周。

**表情与表情包。** 分三层：内置表情集、自定义表情包（用户导入图片或动图，随消息发送文件标识）、常用表情（按使用频次排序）。**不建议做表情商店**——它需要内容源与内容审核，在内网环境下没有意义。工作量约 0.5–1 人周。

**常用联系人。** 表面是排序问题，实质是数据归属问题。需要记录联系频次与最近联系时间，并支持手动置顶与星标；开发量很小，但**数据必须落在服务端**——本方案已确认"换机可登录"，若常用列表只存本机，换一台电脑就丢失，用户会直接判定为缺陷。直连态下的该列表存本地库，登录后与云端合并。工作量约 0.5 人周。

**汇报关系（直属上级）。** 这一项最容易被误当作"部门树上的顺带字段"，实际它是一条**独立于部门归属的数据**。以企业微信为参照：直属上级是成员资料中的独立字段，每人最多设置一名，可在管理后台逐人设置，也可通过花名册批量导入。**这条数据不建立，"看到自己的领导"就实现不了**——只能显示部门负责人，而挂靠部门与实际汇报对象常常不是同一个人（例如挂靠在某部门、实际向另一部门负责人汇报）。因此需要：成员表增加直属上级字段、支持批量导入、支持按上级链路逐级查看。**前置条件是数据从哪来**：由管理后台手工维护，还是从现有 HR／OA 系统同步，须评审组明确（见第十一章）。工作量约 1–1.5 人周，不含外部系统对接。

**通讯录可见性。** 由"谁能看到谁、看到哪些字段"派生。参照商用产品的能力边界，需支持三类控制：隐藏指定部门或成员（被隐藏者在通讯录中不可见、不可搜索，可设白名单例外）；限制指定部门只能查看本部门通讯录；对特定人员（如高管）隐藏部分字段。这一项与合规直接相关——**通讯录含手机号等个人信息，在内网中默认对全员公开，本身就是一个数据保护义务上的缺口**。工作量约 0.5–1 人周。

**办公室位置图。** 实现方式明确：上传楼层平面图（图片或矢量图），在图上标注工位与办公室点位并与成员绑定；使用时按姓名搜索后图上高亮放大，或点击点位反查人员；支持多园区、多楼层切换；管理后台提供拖拽式的点位标注界面。

这一项**开发不难（约 1.5–2 人周），难的是两件事**。

其一，**数据维护是长期负担**。工位会调整、部门会搬迁、平面图会重画。若每次变动都要找开发人员改数据，这套功能上线数月后必然废弃。因此后台的点位编辑器不是"可选增强"，而是**必要组件**，并且必须明确一名维护责任人（通常是行政或 IT 支持岗）。

其二，**办公场所图属于敏感信息**。完整的楼层布局、安防通道、关键设备间位置，在安保意义上并不适合全员可见。建议默认仅开放本人所在楼层，跨园区与跨楼层按需授权；对安保、机要等岗位可整体关闭。此点已列入决策事项。

**远程协助。** 这是本版新增功能中**最重、也最需要先划定边界的一项**。技术上分三档，工作量差异很大：

- **只读模式**（仅查看屏幕，不可操作）：约 1.5–2 人周；
- **可控模式**（增加鼠标键盘注入与剪贴板同步，需逐平台实现）：约 3–4 人周；
- **无人值守模式**（受控端无需在场确认即可连接）：**不建议实现**，风险远超收益。

建议第二期只做"屏幕查看 + 经受控方授权的操作"，且**默认仅对 IT 运维人员开放**。

需说明一点：远程协助领域已有成熟的开源自托管方案，但本项目均不采用。以 RustDesk 为代表的产品采用 AGPL-3.0，其核心代码受传染性许可约束——一旦链接进自有客户端即构成演绎作品，会把本项目的客户端代码一并拖入开源义务，与“不采用开源二开、自有代码自主掌控”的既定路线直接冲突。因此本项目**仅参考其架构分层思路**（信令、中继与编解码分离、受控端确认机制），不复制其代码，实现自行开发。

同时需澄清一点，以免本项结论被误读为“根本没有可选的替代品”。同类产品中另有三个**许可证宽松**的方案，均已评估：

- **MeshCentral**（Apache-2.0）：自带受控端 agent，形态与 RustDesk 最接近，覆盖远程桌面、终端与文件管理；
- **Apache Guacamole**（Apache-2.0）：浏览器远程桌面网关，走 RDP／VNC／SSH，受控端无需安装 agent；
- **FreeRDP**（Apache-2.0）：RDP 协议的客户端侧实现库，可安全链接进自有程序。

三者被排除的原因**不在许可证，而在与本方案硬性要求的冲突**：RDP 与 VNC 的授权模型是操作系统层面的登录，无法承载“受控端本机弹窗、显示发起人姓名与所属部门、由本人点击同意”这一交互要求；而 Windows 的 RDP 远程登录会接管并锁定本地会话，受控方在自己屏幕上反而看不到对方在操作什么，与“过程对受控方持续可见”的要求正好相反。MeshCentral 虽形态同构，但它是包含服务端、控制台与独立账号体系的一整套远程管理平台，与本项目的 IM 账号体系及远程协助留痕表无法对接，集成成本高于自研。

因此结论不变——**远程协助属于“要么自研、要么不做”的一类功能**。但须明确其工作量口径：3–4 人周指的是**受控端的屏幕采集与输入注入、授权交互，以及服务端的操作留痕**三部分，**媒体传输层不在其中**，统一复用第四章第十节的 WebRTC 底座。这一口径是该项能够以该工作量自研成立的前提。

下列四条为硬性要求，应写入开发任务书：

1. **必须由受控方显式确认。** 发起请求后，受控端弹出提示，显示发起人姓名与所属部门，由本人在本机点击同意；任何形式的静默连接都不允许。
2. **过程对受控方持续可见。** 连接期间受控端保持明显的状态提示，且受控方可随时一键中断；不支持隐藏该提示。
3. **全程留痕。** 服务端记录发起人、受控方、起止时间、时长与操作类别；建议默认录制屏幕，作为审计依据。
4. **范围可控。** 管理后台可按部门下发开关，默认可为"仅 IT 部门可用"；人事、财务、机要等岗位的终端可设为不允许被远程控制。

**这一项与其他功能性质不同**：其余功能是数据流动，远程协助是跨终端的操作权限。一旦被滥用，影响面远大于一次消息泄露。第九章将并列说明其合规要求。

**小结。** 六项合计：第一期四项约 3–5 人周（截图 0.5–1、表情包 0.5–1、常用联系人 0.5、汇报关系 1–1.5、通讯录可见性 0.5–1）；第二期两项约 4.5–6 人周（位置图 1.5–2、远程协助 3–4）。

### （五）建议不自主开发的两项功能

**音视频会议。** 该功能涉及媒体服务器（SFU）、信令、音视频编解码、回声消除、抖动缓冲与弱网对抗，是一个独立且门槛较高的技术领域。自研即便投入 8–15 人周，也只达到"勉强可用"的水平，稳定性与体验均难以与成熟产品相比，且后续维护成本持续存在。**建议方案：** 其一，采购具备内网部署版本的商用会议软件；其二，在允许范围内集成开源媒体服务器（如 LiveKit、Jitsi、Mediasoup）并由本项目负责单点登录与界面集成。需注意集成开源组件与"二次开发开源软件"性质不同——前者是部署与调用，不涉及分发自有代码，不受传染性条款约束，但仍须核对其许可证的具体要求。


**此处需澄清一点：不建议自研的是“会议系统”这一层，不是 WebRTC 本身。** 上述开源媒体服务器（LiveKit、Jitsi、Mediasoup）**本身就构建在 WebRTC 之上**——WebRTC 提供的是媒体传输与穿透的标准能力，这些项目在其之上补齐了多人转发（SFU）、信令、房间管理与录制。因此本方案的定位是：**媒体传输底座由本项目统一掌握（第四章第十节），会议系统这一层不重复开发**，按前述方式集成或采购。换言之，“不用 WebRTC”与“不自研会议系统”是两个不同层次的判断，不应混为一谈。
**协同文档（在线文档／表格／知识库）。** 该功能的核心是协同编辑算法（OT 或 CRDT）、富文本编辑器与实时同步，同样是独立领域，自研周期长且细节问题多。**建议方案：** 部署 OnlyOffice Document Server 或 Collabora Online，通过页面嵌入方式集成到本系统的文件模块中，并由本项目统一身份与权限。需注意两者的许可证不同（分别属 AGPL 与 MPL 系），采用前应确认内部使用场景下的合规性。

**这两项不纳入自研范围，是本方案能够按期交付的关键前提。** 若评审组要求二者也自主开发，则项目周期与投入需另做评估，且建议作为独立项目立项，与本项目并行推进而不交叉依赖。

### （六）分期结论

"向企业微信看齐"是一个方向，而不是一份需求清单。将其拆为四期之后，本项目从一个目标模糊的大工程，转变为四项边界清晰、可独立验收的建设任务：

- **第一期解决"能不能替代"**——这是刚需，也是投入产出比最高的一期；
- **第二期解决"够不够好用"**——办公协同能力，增量交付、风险分散；
- **第三期解决"能不能更省事"**——AI 能力，依赖硬件与归档数据；
- **第四期解决"能不能全覆盖"**——建议不自主开发，采购或集成。

另需说明，本版新增的办公室位置图与远程协助落在第二期而非第一期，原因有二。其一，二者不解决"能不能替代"的问题，缺少它们第一期依然可上线可用；其二，远程协助涉及跨终端的操作权限，宜在第一期落地、相关管理制度成型之后再开放该项能力，避免制度未定而能力先行。

建议评审组按此边界审议，并明确第一期即完成验收，后续各期单独立项。

## 三、为何不采用开源方案二开

本章说明技术路线的选择依据。本次已确认不采用开源软件二次开发，本章给出具体理由，供评审组复核该判断。

### （一）可用的开源方案及其定位

国内可用于内网办公的开源即时通讯项目，按部署形态分为三类。

**表 6　开源方案按部署形态分类**

| 类别 | 代表项目 | 是否需要服务端 | 记录存放位置 | 身份来源 |
| --- | --- | --- | --- | --- |
| 免服务端局域网直连类 | 茶话间、iptux、BeeBEEP、nwChat、LAN Messenger | 否 | 终端本机 | 设备自身 |
| 服务端私有化部署类 | 喧喧、Mattermost、Rocket.Chat、Zulip | 是 | 服务端 | 账号 |
| SDK／基础设施类 | OpenIM、野火IM、悟空IM、MobileIMSDK | 是 | 服务端 | 账号，且客户端需自研 |

**免服务端类**（以茶话间、nwChat 为代表）采用纯局域网点对点架构，通过 UDP 广播发现同网段节点，支持单聊、群聊、文件与文件夹传输、断点续传、共享文件柜，并已适配统信 UOS 与麒麟 Linux。其形态与本方案所需的"直连态"高度一致，**代码可作为直连引擎的参考实现**。局限在于：全部不含服务端，聊天记录只存本机，终端重装或员工手动删除即丢失，管理员无法查看任何会话，因此无法满足 R3。

**服务端私有化类**（以喧喧为代表）具备服务端留存能力，采用 AGPL-3.0 许可证，服务端为 Go 语言、客户端基于 Electron 与 React，支持纯局域网运行，内置组织架构、权限、状态监控与信创适配。**这类方案能力最接近本方案所需，但存在下述两处硬伤。**

**SDK 型**（OpenIM、野火IM 等）提供服务端与各平台客户端 SDK，但不提供开箱即用的完整客户端，管理后台亦需自行开发，本质上与自研的工作量相差不大。

### （二）二开路径的四处具体障碍

**障碍一，许可证的传染性。** 喧喧采用 AGPL-3.0，属强 Copyleft 协议：基于其源码改造后，若通过网络对外提供服务，须公开改造后的全部源码。对纯内部使用场景，这一约束不构成直接障碍；但会造成两个实际困扰——其一，后续任何对外延伸的计划都会受限；其二，内部代码需要按开源标准管理，与公司的代码资产管理要求可能冲突。若改用 Mattermost、Rocket.Chat（MIT）可规避此项，但二者中文体验与信创适配较弱，改造量会转到另一个方向。

**障碍二，架构冲突。** 本方案的核心形态是"一个客户端内并存两套引擎"。而喧喧客户端是围绕"已连接服务端"这一前提构建的：会话模型、状态管理、消息流均依赖服务端连接。要使其支持免登录直连态，需在客户端内并行一整套独立子系统——不依赖服务端的状态管理、UDP 广播发现与点对点传输、本地消息库与来源标识、跨态会话识别。**这些内容与喧喧原有架构几乎没有复用关系**，等于在一个既有应用内部再建一个新应用，同时还要承担与既有架构的整合成本。改造工作量并不低于自研，却多了外部依赖。

**障碍三，用户需求的特殊性。** 商用产品的组织架构、权限、信创适配能力确实成熟，但本项目的核心诉求集中在"双引擎 + 留档边界 + 跨态标识"这三项上，而这些恰恰是现有开源项目完全没有实现的部分。可复用的能力集中在非核心区，不可复用的部分却集中在核心区。

**障碍四，规模与维护成本。** 部分开源产品的免费版本存在人数上限（如喧喧免费版限 50 人以下团队），超出规模需采购授权。同时，改造后的代码需持续跟随上游版本合并，形成长期维护负担。

### （三）结论

**不采用开源二开，采用纯自研。**

需要区分两个层面。“不使用开源软件二次开发”指的是**不拿别人的完整产品改造成自己的产品**；而“使用开源组件”——调用一个模型、部署一台媒体服务器、链接一个协议库——是性质完全不同的行为，在许可证宽松时不仅允许，而且是本方案降低成本的主要手段。本章第（一）至（二）节论证了前者不成立，下一节给出后者的边界。

而对于开源即时通讯软件，本方案只将其作为**架构参考与实现参照**，不复制其代码，因此不存在许可证约束。附录 B 列出所参考的项目，供开发阶段查阅。

### （四）组件级许可纪律

在上述结论之上，另需确立一条更细的约束，它管的是**组件**而非整个软件：**本方案不集成任何采用强传染性许可（AGPL／SSPL）的组件，包括不以动态或静态链接方式引入、不与其代码合并编译、不将其修改后对外提供。**

之所以把这条单独写出来，是因为它直接约束开发过程中的技术选择，却极易被一句“开源不是免费的、要注意合规”带过而实际无人执行。本方案在下列各处使用开源组件，均符合该纪律。

**表 7　开源组件使用清单与许可性质**

| 使用场景 | 具体内容 | 许可证 | 引入方式 |
| --- | --- | --- | --- |
| AI 模型 | Qwen 系列、DeepSeek 系列 | Apache-2.0 / MIT | 部署调用，不改造、不分发 |
| 语音识别 | FunASR（达摩院） | Apache-2.0 | 部署调用 |
| 媒体传输（标准） | WebRTC | BSD-3-Clause | 标准与协议对接 |
| 媒体传输（Qt 路线） | libdatachannel | MPL-2.0 | 链接引入，文件级弱传染，允许 |
| 音视频会议 | LiveKit / Jitsi | Apache-2.0 | 部署集成 |
| 协同文档 | OnlyOffice Document Server | AGPL-3.0 | 部署集成，见下述例外判定 |

需要说明三点。

**其一，许可强弱的分界线是“是否形成演绎作品”。** Apache-2.0、MIT、BSD 属宽松许可，可自由链接与分发，只需保留版权声明；MPL-2.0 属文件级弱传染，仅在修改其源文件时要求公开该文件，链接使用不受限；AGPL-3.0 属强传染，一旦链接或合并编译，义务将覆盖整个自有程序，并因网络交互条款而在对外提供服务时同样触发。

**其二，协同文档是本表中唯一的例外，需单独判定。** OnlyOffice 以 AGPL 授权，但本项目只**部署并调用其服务**，不修改源码、不把它的代码链接进自有客户端，因此不构成演绎作品；作为独立程序与服务端并存，属“聚合”而非“合并”，与链接 RustDesk 的情形有本质区别。**这一判定成立的前提是始终保持进程边界**——若后续需要修改其源码或将其嵌入自有服务进程，前提即消失，须重新评估。该前提应写入开发任务书，并在交付时以组件清单形式核实。

**其三，这条纪律同时解释了附录 B 的列示口径。** 该附录列出的项目包含数项 AGPL 软件，它们在报告中的地位并不相同：**RustDesk 与喧喧已明确排除、不构成选型，仅作架构参考；OnlyOffice 属独立进程部署的集成对象**。附录 B 已按此逐项标注。

## 四、总体架构设计

本章给出总体架构，包括双引擎模型、共享内核、跨态互通规则、账号与多端登录模型、归档状态标识、功能权限分层、文件通道的旁路设计以及媒体通道的底座选择。

### （一）双引擎模型

客户端内并存两套相互独立的通信引擎。

**直连引擎（免登录）。** 不依赖任何服务器。启动后通过 UDP 广播向同网段宣告自身并接收其他终端的宣告，据此构建在线设备列表；消息与文件通过 TCP 点对点直达。由于不经过中心节点，该引擎产生的消息**只写入本机数据库，服务端没有任何记录**——这是 R2 的直接要求。安全方面建议采用自定义协议并启用端到端加密（基于 ECDH 的密钥协商加对称加密），而非沿用 IPMsg 的明文报文。

**协作引擎（已登录）。** 用户填入服务端地址并完成登录后启用。客户端与服务端建立长连接，消息经服务端中转并落库；联系人列表、组织架构、群组、云端历史等能力由服务端提供。该引擎的消息**在服务端永久留存**，本机数据退化为缓存性质。

**两套引擎同时运行。** 登录后并不关闭直连引擎，因为跨态互通（第四节）需要已登录用户仍能发现并联系局域网内未登录的同事。这一点与"登录后二者互不干扰"的直觉不同，需在开发中明确。

### （二）共享内核

两套引擎之上是一套共用的数据与交互层。

**本地消息库。** 单一 SQLite 数据库，消息表以来源字段区分直连记录与云端记录，并以同步状态字段标记云端消息的归档情况。两态历史的合并展示依赖该字段，这是"切换模式不丢历史"的技术基础。

**会话列表。** 统一视图，将直连会话与云端会话按时间混合排列，每条会话附带归档状态标记。不提供按来源筛选的开关，避免用户因筛选而误判某段对话已被留存。

**联系人视图。** 合并两态来源：云端下发组织架构，直连引擎提供局域网在线设备。同一人同时以两种身份出现时（已登录且其设备也在广播），按映射规则合并为一条，避免重复条目。

**文件传输模块。** 两个形态共用同一套文件传输实现。协作态下的文件同样走点对点直传、不经服务端，仅由客户端向服务端上报传输元数据。

### （三）运行态与切换

**直连态（默认）。** 安装后直接进入，无需任何输入。处于直连引擎工作状态，可发现并联系同网段终端，聊天记录写入本机。

**协作态（可选）。** 用户填写服务端地址并登录后进入。界面增加组织架构、群组、云端历史等入口，消息开始落入服务端归档。退出登录后回到直连态，本地历史保留，但不再产生新的归档记录。

**降级态。** 协作态下服务端不可达时，客户端自动回落至直连引擎——仍可在同网段内收发消息、传输文件，但消息不再进入归档。**服务端故障因此只影响归档、组织架构与云端历史，不影响基本沟通**，这与单通道架构下"服务端故障即全员失联"有本质区别。

### （四）跨态互通规则

已登录用户与未登录用户之间可以互相通信，链路自动降级为点对点直传。这是本架构中需要评审组重点理解的一处设计，因为它直接决定归档的完整性。

**可达性。** 已登录用户的直连引擎持续运行，能够发现局域网内处于直连态的终端；未登录终端通过 UDP 广播发现的"已登录同事"，其广播标识中携带账号信息，因此显示为正常姓名而非陌生设备。

**消息路径。** 跨态会话的消息**不经服务端、不进入归档**，只写入双方的本地数据库，行为与该会话在直连态下完全一致。

**界面标识。** 凡跨态会话，会话标题右侧显示"未归档"标记，输入框上方固定显示说明文字。该标识不可关闭，确保用户每次输入时都能看到该对话不会被留存。

**归档起点。** 同一条会话可能先处于跨态（不归档）、后因对方登录而转入协作态（归档）。此时服务端归档的是**登录之后的消息**，管理后台在该会话的归档记录起始处标注"归档自某时刻"。**归档以消息为单位判定，而非以会话为单位**，这是留档口径上必须明确的定义。

**风险与对策。** 该通道存在被利用以规避留存的可能——员工可与同事约定"你退出登录，我们用直连通道聊"。对策有三：其一，提供"允许与未登录设备通信"策略开关，对归档要求高的部门直接关闭该通道；其二，客户端记录跨态会话的建立日志（时间、双方、时长）并上报服务端——**上报的不是消息内容，而是"发生过一次不经归档的通信"这一事实**，使异常频繁的跨态通信可被察觉；其三，在员工告知材料中如实写明留档边界。

### （五）账号与多端登录模型

本版对该模型做了修正。上一版将需求理解为"账号锁死在指定终端"，本次明确为**企业微信式的多端登录管控**。

**可登录性。** 账号可在任意已注册设备上登录，换机不受限制。登录时客户端采集本机设备指纹，服务端据此识别设备并在登录记录中登记。

**终端分类。** 终端划分为桌面端（Windows、国产 Linux、macOS 归为一类）、移动端与网页端。

**在线策略。** 桌面端同一账号**仅允许一个在线**：在另一台电脑登录时，前一个客户端被强制下线并收到明确提示。桌面端与移动端可以同时在线。该策略与企业微信一致，既满足换机使用，又避免多台电脑同时在线导致消息状态混乱与责任不清。

**登录记录。** 每次登录留存：账号、设备指纹、设备类型、设备名称、登录时间、来源地址、客户端版本。用户侧提供"登录设备管理"入口，可查看当前及历史登录设备并主动下线其他端；管理侧可查询全员的登录记录。

**设备指纹的用途随之调整。** 它不再承担"锁死登录"的职责，而用于三件事：其一，直连态的身份标识；其二，设备台账（设备与使用人的对应关系）；其三，登录记录与异常检测（如同一账号短时间内在多台设备登录）。由于不再要求凭据与机器绑定，**不存在"员工换台电脑就登不上、必须管理员解绑"的问题**，运维成本明显降低。

**新设备首次登录的管控。** 建议保留"新设备需审批或邮件确认"的开关，避免账号被他人凭密码在陌生设备上使用。

### （六）归档状态标识

由于归档范围随会话形态而定，界面必须让用户对"这条对话是否会被留存"有确定认知。

**表 8　会话归档状态标识**

| 会话类型 | 界面标识 | 含义 |
| --- | --- | --- |
| 双方均已登录 | 无标识（默认） | 经服务端中转，全部消息进入归档 |
| 一方未登录（跨态） | 显示"未归档" | 点对点直达，双方本地保存，服务端无记录 |
| 曾跨态后转为协作态 | 显示"归档自 X 时刻" | 转协作态之后的消息进入归档，之前的无记录 |

该标识同时承担两项功能：对用户，明确留档范围，使员工告知材料的表述与产品行为一致；对管理员，解释为何某些对话在后台查不到，避免被误判为系统漏记。

**关于撤回，需在界面文案上把握一点。** 撤回后客户端不再显示原消息，但**归档状态不变、归档内容不变**——该条消息在服务端仍为原文，并额外附带一条撤回事件记录。因此撤回的提示语应表述为"消息已撤回"，**不得出现"已删除""不再保存"一类会造成误认的措辞**。这与第一章第二节的排除项一致：系统提供撤回，但不提供"撤回即可消除留痕"。

### （七）功能权限分层

**表 9　两种运行态的功能权限划分**

| 功能 | 直连态（未登录） | 协作态（已登录） |
| --- | --- | --- |
| 一对一文本消息 | 支持 | 支持 |
| 点对点文件互传 | 支持 | 支持 |
| 与未登录同事通信 | 支持 | 支持（受策略开关约束） |
| 联系人列表 | 仅可见同网段在线设备 | 可见完整组织架构 |
| 群聊 | 支持（免服务端的临时群组） | 支持（含群公告、群文件、群工具） |
| 共享空间 | 只读 | 按角色读写 |
| 私有云盘 | 不可用 | 支持 |
| 历史记录云端同步 | 不可用 | 支持，换机可迁移 |

该分层同时承担一项管理功能：它使"登录"成为一个有实际收益的动作——云端历史、换机不丢、组织架构、私有云盘、群工具都只在登录后提供——从而引导员工主动完成账号绑定，使设备台账与人员信息的对应关系日趋完整。

### （八）策略开关

方案提供三个由管理后台按部门下发的策略开关。

**表 10　策略开关**

| 开关 | 默认 | 作用 | 适用场景 |
| --- | --- | --- | --- |
| 允许免登录使用 | 开启 | 关闭后未登录客户端无法进入主界面，退化为常规企业 IM | 高保密部门、涉密岗位 |
| 允许与未登录设备通信 | 开启 | 关闭后已登录客户端不再响应跨态发现与消息，跨态会话无法建立 | 对归档完整性要求高的部门 |
| 新设备登录需审批 | 开启 | 账号首次在陌生设备登录需管理员审批或邮件确认 | 全部部门 |

三者组合的效果为：全部开启时接入最宽松、体验最接近飞秋；"允许与未登录设备通信"关闭时归档无缺口，但员工无法联系未登录同事；"允许免登录使用"关闭时该部门退化为账号强制形态。

### （九）文件通道的旁路设计

归档若字面执行到文件上，意味着数百兆至数吉字节的字节流需要经过服务端中转，服务端的磁盘写入与网络带宽将成为瓶颈，传输体验反而劣于移动介质。

因此文件传输在两个形态下均采用**旁路设计**：文件字节流由收发双方在局域网内直接传输，不经过服务端；协作态下服务端仅接收并保存**传输元数据**，包括文件名、大小、文件哈希、发送方、接收方、发起时间与是否接收。元数据已能证明"谁在什么时间向谁传递了哪个文件"，足以支撑责任追溯；文件本体是否归档作为可选项，按部门维度开启。

直连态限于本网段；跨网段场景下文件传输改走协作态，或提供经由服务端转发的降级路径，但默认关闭，仅在明确需要时按文件大小阈值放行。

### （十）媒体通道的底座选择

本方案的媒体类能力——远程协助的画面流、音视频会议的媒体流以及屏幕共享——共用同一条传输通道。这一层不做两套实现，**统一以 WebRTC 为标准底座**。

选择理由有三。**其一，它解决的正是最不该自行实现的部分**：媒体传输（SRTP／DTLS）、NAT 穿透（ICE／STUN／TURN）、拥塞控制与自适应码率，都是经过长期工程积累才稳定的问题，自行实现既不现实，也不产生任何差异化价值。**其二，在本项目的网络条件下它的边际成本极低**：同一网段内的两台终端仅凭主机候选地址即可直接建立连接，连 STUN 服务都不需要；跨网段与跨地域场景下，第八章确定的集中协作服务端可**同时兼任 TURN 中继**，无需为媒体单独增加服务器。**其三，许可证干净**：WebRTC 是 W3C 与 IETF 标准，参考实现采用 BSD-3-Clause，与第三章第四节确立的组件许可纪律完全一致——这也正是本项目能够绕开 RustDesk（AGPL-3.0）而自行实现远程协助的前提。

但同样必须明确 **WebRTC 不提供什么**。它是一条管道，不包含管道两端的能力。

**表 11　WebRTC 的能力边界与本方案的取得方式**

| 能力层 | WebRTC 是否提供 | 本方案的取得方式 |
| --- | --- | --- |
| 媒体传输（音视频、屏幕画面流） | 提供 | 直接使用 |
| 数据通道（控制指令、剪贴板、小文件） | 提供 | 直接使用 |
| NAT 穿透（ICE／STUN／TURN） | 提供 | 同网段直连；跨网段由协作服务端兼任中继 |
| 拥塞控制与自适应码率 | 提供 | 直接使用 |
| 屏幕采集 | 不提供 | 按操作系统分别实现，Windows、macOS 与国产 Linux 各一套 |
| 键盘鼠标注入 | 不提供 | 按操作系统分别实现，仅远程协助使用 |
| 多人转发（SFU） | 不提供 | 不自研，集成 LiveKit 或 Jitsi（第二章第五节） |
| 授权确认与操作留痕 | 不提供 | 自行实现，记录写入服务端远程协助表 |

由此即可界定远程协助的自研范围：**传输与穿透复用 WebRTC，自研内容集中在受控端的屏幕采集、输入注入、授权交互，以及服务端的操作留痕。** 第二章第四节给出的 3–4 人周即指这一范围，不含传输层。

**媒体流的留痕口径需一并明确。** 本方案确立“连接服务端即为了留痕”，但该原则落实到媒体流上需区分对象：**媒体内容本身不落地存储**——一段三十分钟的通话或远程协助录屏，其存储与带宽开销均不可承受，这与文件通道不归档字节流出于同一考量。取而代之的是**归档“发生过这次通信”这一事实的元数据**：参与方、起止时间、时长、连接方式（直连／中继）与媒体类型。其中远程协助的屏幕录制作为可选开关按部门下发，录制文件独立存储，适用与归档消息相同的留存期。

这样处理的理由与文件通道完全一致：**留痕的目的是可追溯、可举证，而非保存每一帧画面。** 元数据已足以回答“谁在什么时间与谁进行了何种性质的通信”，而这正是审计所需的信息层级。

## 五、自研方案设计

本章给出自研方案的具体设计，包括模块划分、数据模型、客户端技术选型、工作量估算与资源需求。

### （一）模块划分

**客户端**由五个模块构成：直连引擎、协作引擎、共享内核（本地库、会话、联系人、文件传输）、界面层、系统集成层（托盘、通知、开机启动、多端互踢）。

界面层之上另有一组工具化组件，对应本版补充的体验功能：截图与标注、表情与表情包管理、常用联系人、办公室位置图视图、远程协助会话窗口。其中**远程协助是客户端内唯一需要按操作系统分别实现的部分**——屏幕采集与输入注入在 Windows、macOS 与国产 Linux 上接口各不相同，无法复用同一套代码。

**服务端**由六个模块构成：接入网关（长连接与消息路由）、账号与设备（认证、设备台账、多端在线管控）、组织架构（部门、成员、角色、权限）、消息与归档（存储、检索、导出）、策略服务（开关下发）、文件元数据服务。

**管理后台**由四部分构成：成员与部门管理、权限与角色配置、设备台账与登录记录、消息检索与审计。

### （二）数据模型

核心表结构如下。

**账号表（accounts）**：账号标识、姓名、工号、部门、直属上级、角色、状态、密码摘要。其中**直属上级为独立字段**，每人至多一名，是"查看自己的领导"这一需求的唯一数据来源——它不能由部门归属推导得出。

**设备表（devices）**：设备指纹哈希、设备类型（桌面／移动／网页）、设备名称、操作系统、绑定使用人、首次注册时间、最后活跃时间、状态（正常／停用／待审批）。

**登录记录表（sessions）**：会话标识、账号标识、设备标识、设备类型、登录时间、失效时间、来源地址、客户端版本、在线状态、被踢原因。该表是 R4 的实现基础。

**组织架构表（departments）**：部门标识、上级部门、部门名称、排序、负责人。

**会话表（conversations）**：会话标识、类型（单聊／群聊）、名称、创建者、创建时间、归档起点标记。

**成员关系表（conversation_members）**：会话标识、成员标识、成员类型（账号／设备）、加入时间、角色（群主／管理员／成员）、是否静音。

**消息表（messages）**：消息标识、会话标识、发送方账号标识、消息类型、正文内容、发送时间、送达状态，以及**撤回标记与撤回时间**。为满足 R3，协作态消息**在服务端永久留存**；**撤回只在记录上置标记，不修改也不清除正文**，原始内容与其发送时间保留不变。**直连态消息不写入本表**，该边界由架构决定而非实现取舍。

**传输记录表（transfers）**：文件名、大小、哈希、发送方、接收方、发起时间、是否接收、完成时间。与消息表分离，因为文件元数据字段差异较大，且留存策略可能独立调整。

**策略表（policies）**：部门标识、策略项、取值、生效时间。用于各项策略开关的按部门配置，包括免登录开关、跨态通信开关、新设备审批、远程协助开放范围、位置图可见范围等。

**楼层图（floor_maps）**：图标识、园区、楼栋、楼层、图片路径、版本、可见范围、上传时间。可见范围用于限定该图对哪些部门或人员开放。

**工位点位（seat_points）**：点位标识、图标识、成员标识、横纵坐标、类型（工位／办公室／会议室）、备注。点位与成员绑定后，即可同时支持"按姓名搜索定位"与"点击点位反查人员"两个方向的查询。

**远程协助记录（assist_sessions）**：会话标识、发起人、受控方、开始时间、结束时间、时长、操作类别（只读／可控）、授权方式（本机确认／管理员代批）、录制文件标识、中断原因。该表是远程协助审计的唯一依据，**只可追加，不可修改与删除**。

### （三）客户端技术选型

候选方案有三。**本版在原有的开发效率、打包体积、国产系统适配三个维度之外，增加第四个维度：媒体能力，即 WebRTC 在目标运行环境中的可用性。** 该维度直接决定远程协助、音视频会议与屏幕共享能否落地，而三个候选方案在这一项上的差异是量级级别的——一项“开箱即得”，一项“需要额外投入但可控”，一项“在国产系统上根本不可用”。

**Qt（C++ 或 QML）。** 优势在于：本方案需在客户端内运行持续监听的 UDP 服务与点对点 TCP 连接，Qt 的网络与本地库支持成熟；飞秋与 nwChat 均采用该路线，有较多可参照的实现；在国产 Linux 上的部署问题最少；打包体积小、内存占用低，适合配置较低的老旧办公终端。劣势是界面开发效率低于 Web 技术栈。**媒体能力方面，需引入 libdatachannel（MPL-2.0，可安全链接）或自行编译 WebRTC 参考实现（BSD-3-Clause），预计增加 1–2 人周。** 这一投入换来的是媒体链路的完全可控——而屏幕采集与输入注入本就要按操作系统分别实现，与传输库的选择互不干扰。**若终端硬件跨度大、国产系统占比较高，仍建议优先评估此项。**

**Tauri（Rust + Web 前端）。** 打包体积小、内存占用低，界面用 Web 技术开发效率高，网络能力通过 Rust 侧实现。适合团队有前端储备的情况。**但媒体能力上存在一个必须先核实的阻塞性风险：** Tauri 在 Linux 上使用系统 WebView 引擎 WebKitGTK，而主流发行版打包的 WebKitGTK 默认未启用 WebRTC 编译选项，`RTCPeerConnection` 对象为未定义。这一现象已有开发者在 Deepin 上明确报告，社区反馈上游仍在处理（涉及发行版打包策略）。**这意味着 Tauri 路线在国产 Linux 终端上无法使用 WebRTC**，而国产系统正是本项目的必覆盖目标。若仍选此路线，媒体能力须由 Rust 侧另行实现（如 webrtc-rs），工作量与不确定性均需重估，且与“用 Web 技术提效率”的初衷背离。**在国产系统覆盖要求明确的情况下，不建议采用此项。**

**Electron（Node + Web 前端）。** 开发效率最高，生态最成熟，**媒体能力开箱即得**——Chromium 内核内置完整的 WebRTC 实现，屏幕采集可直接使用其桌面捕获接口，无需额外投入。劣势仍是打包体积与内存占用明显偏大，在老旧的国产系统终端上需实测，这是需要通过实测排除的风险，而非结构性障碍。

**综合结论：以 Qt 为首选，Electron 为次选，Tauri 在国产系统覆盖要求明确的前提下不建议采用。** 判断依据是两类劣势的性质不同——**Electron 的体积与内存劣势是可测量的、可通过硬件摸底排除的；Tauri 在国产系统上缺失 WebRTC 则是阻塞性的，无法通过投入弥补。** 若项目分期推进、媒体类功能确定排在第二期及以后，也可先以 Electron 快速完成第一期，待媒体功能立项时再评估是否迁移；但迁移成本较高，不建议将此作为默认路径。

### （六）系统标识与命名规范

本节确定系统的对外标识与命名依据。**命名在本方案中不是装饰性事项。** 由于第三章已明确排除一批 AGPL 许可的开源项目，系统的名称必须与这些被排除的对象保持距离；否则在交付时的组件清单与合规说明中，容易把「本项目」与「被评估并排除的项目」混为一谈。

**英文名与代号确定为 Memex，中文正式名沿用「内网办公即时通讯系统」。** Memex 一词出自 1945 年万尼瓦尔·布什（Vannevar Bush）提出的「记忆扩展机」（memory extender）构想——一台让人能够按自己的联想路径检索全部既有记录的机器。本方案的核心原则是留痕，而留痕的实质不是「存下来」，而是「将来能找回来」，与这一构想的立意一致。名称须同时满足四条约束。

- **不与已排除的开源项目同名。** RustDesk、喧喧、MeshCentral、Apache Guacamole、FreeRDP 等已在第三章与附录 B 中评估并排除，名称不得与之重叠。
- **不与商用办公通讯产品近似。** 企业微信、飞书、钉钉以及 Slack、Teams、Mattermost 等均须避开，以免在商标与采购口径上产生歧义。
- **不暗示私密或监控。** 名称中不得出现指向「密聊」「阅后即焚」的词根，这与本方案明确的排除项直接冲突；同时应避开 Trace、Track、Guard 一类「追踪」语感——客户端将安装到每一台办公终端上，名称带监控意味会放大推广阶段的心理阻力。
- **可直接作为标识符使用。** 名称须为纯 ASCII、不含连字符、不以数字开头，能够直接用作仓库名、包名、Windows 服务名与内网域名。

## 六、AI 能力规划（第三期）

本章给出 AI 能力的规划。按本次确认，AI 能力列为第三期，在沟通与办公能力上线后再行推进，但需在本报告中说明其前置条件与投入规模，以便评审组一并知悉。

### （一）内网部署的硬约束

**不连外网，模型就必须部署在内网。** 公网大模型接口全部不可用，只能用开源模型本地推理。由此产生三项约束。

第一，**效果上限由模型规模决定。** 受限于可采购的硬件，本地模型的能力与主流商用模型存在差距，尤其体现在复杂推理与长文本理解上。会议纪要、需求整理这类"信息抽取与结构化"任务受影响较小，而"复杂逻辑推理"类任务受影响较大。

第二，**响应速度与并发受限于显存。** 本地推理的吞吐与并发能力直接取决于显存容量，全员高频使用需要相应规模的硬件支撑。

第三，**硬件采购是前置条件。** 该期工作必须在硬件到位后启动，否则无法验证效果。

### （二）硬件门槛

本地部署的核心约束是**显存**，而非代码工作量。

| 7B–9B | 约 6–8 GB | 单张消费级显卡，或 CPU 推理（较慢） | 短文本摘要、简单问答；长会议记录明显吃力 |

### （四）三个应用场景的落地方式

**场景一，群内智能助手。** 群内 @ 机器人即触发。服务端将该群近期的消息按时间窗口取出，结合向量检索召回相关历史片段，组装为提示词送入模型，生成答复后回到群内。技术要点有三：上下文需做滑动窗口加摘要压缩，否则长群的历史无法全部放入；答复须标注"由 AI 生成"，避免被误认为某位同事的发言；读取范围严格受群成员权限约束，机器人不得读取用户不在的群。

**场景二，会议纪要生成。** 输入可以是一段时间的群聊记录，也可以是会议录音的转写文本。服务端做分块摘要（先分块提炼、再汇总成篇），输出固定结构：会议主题、时间、参会人、讨论议题、结论、待办事项（含责任人与截止时间）、下次会议安排。**质量保障的关键是保真与可追溯**——纪要中的每条结论与待办应可回溯到原始消息，界面提供跳转；同时明确标注"AI 生成，仅供参考，以原始记录为准"。

**场景三，需求整理。** 面向"需求对接群"这类场景，将群内散落的讨论整理为结构化需求条目：需求描述、提出人、提出时间、优先级、涉及模块、验收标准、状态。技术要点是**模型必须输出结构化数据（JSON）而非文章**，可通过约束解码或提示词模板实现；输出结果写入需求表后，可被后台当作工单管理，形成闭环。

### （五）模型接入层设计

本节回答一个具体问题：**AI 层能否同时支持本地模型与外部 API 的接入。** 答案是接口层面应当支持、并且必须设计为可插拔，但运行层面受网络与合规约束。两者需要分开说明。

| --- | --- | --- |
| 软件支持多种模型端点 | 能，且应当设计为可插拔 | 统一采用 OpenAI 兼容协议即可，实现成本很低 |
| 接入互联网上的外部 API | 接口能够调用 | **网络不通**——内网与公网物理隔离，外部端点不可达 |

因此结论是：**架构上做成可插拔，运行上默认只能用本地模型。** 这两条并不冲突。

**模型网关的职责。** 在 AI 服务与模型之间增加一层模型网关，统一承担五件事。其一，**协议统一**——采用 OpenAI 兼容接口，本地 vLLM、Ollama 与多数云端服务均原生支持，更换端点只需改配置、不必改代码。其二，**端点注册表**——记录端点名称、地址、凭据、上下文窗口、能力标记（是否支持工具调用与结构化输出）与可用范围。其三，**路由**——按任务类型、数据密级与可用性三条维度选择端点（见表 18）。其四，**健康检查与降级**——主端点不可用时自动切换备用，本地模型排队拥塞时亦可视配置分流。其五，**调用审计**——记录调用者、时间、所用端点、输入规模与所读取的消息范围。

**表 18　模型路由策略**

| 任务类型 | 数据范围 | 允许的端点 | 说明 |
| --- | --- | --- | --- |
| 消息摘要、会议纪要、需求整理、智能检索 | 归档消息 | **仅本地模型** | 硬约束，不由配置决定 |
| 通用问答、公开资料整理 | 不含归档数据 | 本地模型；如具备合规互联网出口可放外部端点 | 需管理员显式注册与开启 |
| 开发期效果基线对比 | 脱敏样本 | 外部端点（限开发环境） | 用于评估本地模型与商用模型的差距 |

**三项必须写死在代码里的约束。** 这三条比"支持外部 API"本身更重要，因为防的是数据外泄。

第一，**归档消息只允许送本地模型。** 判断依据是**数据的来源标记**，而非提示词内容——不得采用"检测提示词中是否含敏感词"这类方式决定路由。该条一旦做成可配置项，一次误配置即构成一次数据外泄事件。

第二，**外部端点默认全部禁用。** 需管理员在后台显式注册并开启，同时记录开启人、时间与用途，供审计追溯。

第三，**出网行为独立告警。** 模型网关产生任何对外连接，无论成功与否，均须写入审计日志并触发告警，不得静默通过。

**该设计带来的两项实际收益。**

其一，**第三期的软件工程部分可不依赖硬件进度。** 提示词工程、上下文组装、结构化输出解析、检索增强等工程内容可先在开发环境以外部端点完成与验证，待 GPU 到位后仅更换端点配置、不改代码。这使硬件采购周期与开发进度解耦——考虑到 GPU 采购周期较长，这一点具有实际意义。

其二，**未来具备互联网出口时零改造。** 若单位后续在互联网区开通合规的大模型服务，或采购厂商的私有化版本（其本质同样为标准 API 端点），只需在网关注册一个端点，客户端与 IM 服务端均无需修改。

**需一并说明的合规前提。** 若本单位涉及涉密等级，外部 API 应一律禁止。此时本节的网关设计仍然成立，其价值转为统一本地多模型端点的管理与审计，并为将来的合规变更预留空间。

### （六）架构设计

AI 能力以独立服务的形式部署，与即时通讯服务解耦。

**IM 服务端 → AI 服务 → 模型网关 → 模型层。** IM 服务端提供消息归档作为唯一数据源；AI 服务负责上下文组装、提示词模板管理、结构化输出解析与检索增强；模型网关负责端点注册、路由、降级与调用审计（详见第五节）；模型层包含大模型推理、向量检索与语音转写三个能力。AI 服务可独立升级、独立扩容，不影响即时通讯服务的稳定性。

**权限是第一原则。** AI 服务读取消息时必须携带调用者身份，按该身份在 IM 系统中的权限范围取数，**不得出现"AI 能读到用户本无权查看的消息"这类越权**。这是本模块最关键的安全设计点。

**AI 产出物的归档规则。** 建议将 AI 生成的纪要与需求条目作为**独立类型的内容**存储，标注生成时间、生成模型、输入范围与生成人，不与原始消息混同。原始消息仍按既定规则归档，AI 产出物可单独清理。

### （七）前置条件与工作量

**启动前置条件有三：** 其一，GPU 硬件到位并完成部署验证；其二，第一期消息归档与权限体系已上线并稳定运行；其三，明确 AI 可读取的消息范围与合规边界，并完成员工告知。三条不满足则不建议启动。

**工作量：** 约 6.5–8.5 人周（不含硬件采购与部署环境准备）。

**另需说明的一项成本：** GPU 服务器的一次性采购成本很可能**高于整个即时通讯系统第一期的开发投入**。这一项应在立项时单独列示，避免与软件开发费用混淆。

## 七、局域网文件共享配套方案

文件共享与即时通讯的业务耦合度较低，建议独立部署一套文件平台，比将其嵌入客户端更稳妥：升级互不影响，权限模型也更清晰。客户端内的文件柜定位于"临时快速传递"，集中化的共享目录由独立平台承担。

### （一）选型要点

选型时有一条容易忽略但必须检查的要点：**项目的维护活跃度。** 本次调研发现，曾广泛使用的轻量级文件管理项目已停止维护并归档仓库，此后不再发布新版本、不再修复缺陷与安全漏洞。此类项目不应再用于新建生产环境。应将"维护活跃度"列为与功能、许可证同等重要的评估项。

### （二）方案对比

**表 19　文件共享方案对比**

| 方案 | 形态 | 优势 | 局限 | 适配场景 |
| --- | --- | --- | --- | --- |
| Samba | 网络共享目录 | 操作系统自带，Windows 映射网络驱动器后体验与本地盘一致 | 权限依赖系统账户，无法按通讯身份统一管控 | 只需目录级共享、终端以 Windows 为主 |
| Cloudreve | Web 文件平台 | 中文界面友好，支持用户组与配额、分享链接密码与有效期 | 需另行维护账号体系 | 需要 Web 端访问与分享链接 |
| Kodbox | Web 文件平台 | 类 Windows 桌面式操作，上手成本低 | 资源占用高于轻量方案 | 用户习惯桌面式操作 |
| Seafile 社区版 | 同步盘 | 分块去重、增量同步速度快，有桌面与移动客户端 | 部署组件较多 | 需要多终端自动同步 |

### （三）建议

**建议采用 Samba 与 Web 文件平台组合的方式。** 日常办公最频繁的需求是"像访问本地磁盘一样访问共享目录"，Samba 在这方面体验最好、零额外维护；对于需要 Web 端访问、外发分享链接或按人授权的场景，额外部署一套 Web 文件平台作为补充。Web 文件平台建议选用活跃维护的 Cloudreve 或 Kodbox。

若希望共享空间与通讯身份统一，需在登录环节做设备凭据对接，或将访问权限收敛到部门级共享目录、弱化个人账号概念。具体做法应在实施阶段的技术方案中细化。

无论采用哪种方案，都应遵循三条原则：**权限按最小必要授予**；**共享内容纳入留存管理**，与聊天记录采用一致的留存期限；**区分快速传递与集中共享**。

## 八、网络拓扑与部署规划

本章说明系统在多网段与多地域环境下的部署形态与配套要求。经确认有两条：其一，协作服务端采用**单台集中部署**，不设地域边缘节点；其二，**免登录直连态限于本网段，定位为临时、就近使用**。两条合起来得到一个清晰的分工——**跨网段与跨地域的沟通全部由协作态承接**。

### （一）跨网段的两个独立问题

直连态的自动发现依赖 UDP 广播（端口 2425），而路由器与三层交换机默认不转发广播——这是网络设备的基本行为，并非配置不当。

**本方案对此的结论是：不为直连态解决跨网段发现。** 免登录直连态定位为**本网段内的临时、就近使用**，跨网段与跨地域的沟通一律通过登录接入协作态完成。因此本章以下内容只作原理说明与部署形态交代，**不构成开发任务，也不产生对网络管理员的配置要求**。

即便如此，"**发现**"与"**可达**"这两件事仍值得区分清楚，因为它决定了一个常见误判——是否要为此开发一套中转服务。

**发现**：广播出不了本网段，因此跨网段的终端相互看不见。这一环若要解决，必须依赖网络设备配合，无法在应用层绕过。

**可达**：发现之后消息走点对点单播。只要两个网段之间三层路由可达（能互相 ping 通），单播直连即可成功，**不需要网关，消息也不经过任何中转**。

由此得到一条简洁的判断规则：**路由可达时，只需解决"发现"；路由不可达时，才需要真正的中继转发。** 常见误区是把这两件事混为一谈，将"配一条设备命令"即可解决的问题做成了"开发一套中转服务"。本方案不走这条路，理由见本章第八节。

### （二）四种网络场景与两态分工

**表 20　各网络场景下两种运行态的分工**

| 场景 | 典型情况 | 直连态的可行性 | 协作态 | 需要什么 |
| --- | --- | --- | --- | --- |
| 同网段 | 同一 VLAN 内的终端 | **可用**：UDP 广播发现、点对点直连 | 可用 | 零配置 |
| 跨 VLAN、三层可达 | 同园区不同 VLAN，核心交换具备路由 | 需网络设备配置才能发现，**本方案不安排** | **可用** | 登录即可，无需网络改造 |
| 跨 VLAN、三层不可达 | 网段间被防火墙或 NAT 隔离 | 不可用 | **可用** | 登录即可，无需网络改造 |
| 多地域 | 异地分部，经专线互联 | 不可用，且不建议启用 | **可用** | 专线或加密隧道接入服务端 |

这张表也是"为什么不必为跨网段做额外投入"的直接回答：**从第二行起，协作态已经天然可用，且不需要任何网络侧改造**；直连态在这些场景下缺失并不影响业务——它本就不是为跨网段设计的。

**关于 UDP 广播的三点说明（理解用，不构成实施任务）。** 其一，网络设备默认只转发 TFTP、DNS、DHCP、NetBIOS 等固定端口，**2425 不在默认列表内**；将来若确有跨网段直连的需求，需要网络管理员显式放行并配置 UDP 中继（Cisco 系为在接口下增补该 UDP 端口，华为、H3C 系为在接口下配置 UDP Helper 并指定目的地址）。其二，即便配置中继，也只能**定向转发到指定地址**，不能把广播扩散到全网段。其三，**在多个网段之间用软件中继实例互相转发广播包的做法应予避免**——每个网段将收到全部网段的广播，单点看到的广播量为原来的 N 倍，全网总量按 N 的平方增长，反而制造稳定性问题。以上三点仅作为将来需求变化时的参考，本版不安排。

**端口固定化仍然保留。** 直连态应使用固定端口段（建议 UDP 2425–2436、TCP 2426–2437）。即便只在本网段使用也应如此——端口不固定会让安全策略无法编写，也会给后续排查与准入控制带来困难。

### （三）部署拓扑

经确认，**协作服务端采用单台集中部署**，部署于总部机房，集中承担接入网关、消息转发、消息归档、组织架构、管理后台与 AI 推理六项职责。各地域客户端通过专线或加密隧道接入同一服务端，不设地域边缘节点。服务端在配置、证书与文档中统一使用内部域名与主机名标识（内网域名以 memex.corp.local 为示例，按实际情况替换），与第五章第六节的命名规范保持一致。

选择单台集中部署的理由有三。

其一，**架构与运维最简。** 无需处理地域节点与中心之间的数据同步、版本一致性、故障切换与分布式事务，运维对象从"多地多套"降为"一处一套"。

其二，**服务端故障不会导致全域失联——这是单台部署在本方案中风险可控的根本原因。** 本方案为双引擎架构：协作态下服务端或专线不可达时，客户端自动回落至直连引擎，本网段内的消息收发与文件传输仍然可用。换言之，服务端是**归档与管理能力的单点**，而非**通信能力的单点**。这一点与常规中心化即时通讯系统有本质区别，也是单台部署可被接受的前提。

其三，**投入最低。** 避免了每地域一台节点服务器及其配套运维成本。

**直连态的边界：本网段。** 免登录直连态仅在本网段内工作，跨网段与跨地域沟通一律通过登录接入服务端。理由有三：免登录形态的核心价值在于"零部署、装完即用"，跨网段或跨地域必然要求部署节点、配置隧道并处理时延，该价值随之消失；跨地域点对点连接在带宽与策略上通常难以保障，实际流量仍需回落到中继；且一条不受管控、可跨域通信的通道在合规上难以解释。详见本章第八节。

### （四）三项工程约束

**地址规划不得冲突。** 多地域互联后，若各地域使用相同网段（例如均使用 192.168.1.0/24），将产生路由冲突。这是多地域互联中最常见的实施障碍，必须在部署前统一规划并纳入网络改造范围。

**时钟统一。** 消息归档、登录记录与审计日志均依赖时间戳。各地域终端与服务端必须接入统一时间源（NTP），否则跨域会话的消息顺序与取证时间会出现偏差。

**链路加密。** 跨地域链路若经过非受控路径，应按等级保护要求启用加密（IPsec 或国密隧道）。链路层加密与协作引擎自身的应用层加密相互独立，两者都应具备。

### （五）单台集中部署的三项影响与对策

**时延。** 异地员工登录、拉取组织架构、检索历史消息均需跨城访问，感知上会慢于本地部署。对策：客户端对组织架构与常用会话做本地缓存并增量同步；历史消息分页按需拉取，不做全量预载；管理后台的全局检索允许异步返回结果。

**链路中断与归档缺口。** 这是单台集中部署必须明确的第一项规则。协作态下服务端或专线不可达时，客户端回落至直连态，消息不经服务端、不进入归档，形成归档缺口。此处有两种处理方式，需评审组确认。

**方式一（建议）**：协作态下**双方均为已登录用户**时，中断期间的消息在本地暂存，连接恢复后自动补传归档；只有与未登录用户的会话才真正走直连、不归档。补传时由服务端按客户端生成的消息标识去重，避免双方重复上报。该方式将归档缺口压缩到"与未登录同事的会话"这一类，代价是客户端需增加暂存队列与补传机制，工作量约 0.5–1 人周。

**方式二**：沿用现有设计，中断期间的协作态消息直接降级为直连、不归档。实现简单，但归档缺口随中断时长同步扩大。

**单点风险。** 服务端集中部署意味着归档、组织架构、云端历史与 AI 能力集中于一处。对策：数据库定期备份并验证恢复流程；准备冷备机与切换预案；以直连态作为基本沟通的兜底；公示维护窗口，并在客户端明确提示当前已回落至直连态、消息不会进入归档。

### （六）服务端资源规格

单台服务端承载全域并发，规格须按**全域注册人数**而非单地域人数估算。

**表 21　服务端规格分档建议**

| 全域规模 | 建议配置 | 部署方式 | 说明 |
| --- | --- | --- | --- |
| 200 人以内 | 8 核 16 GB | 接入网关、数据库与应用同机 | 第一期起步档位 |
| 200–500 人 | 16 核 32 GB | 数据库独立部署，消息存储使用独立卷 | 存储起步 500 GB 并按留存期限规划 |
| 500 人以上 | 按压力测试结果定档 | 接入网关、数据库、文件元数据与 AI 推理分离部署 | 此时"单台集中部署"应理解为**逻辑单套**而非物理一台，中心化架构本身不变 |

**带宽评估。** 跨地域链路需承载消息、组织架构同步、登录与历史检索流量；文件字节流走旁路、不占用跨地域链路，因此专线带宽需求不高，但需按消息峰值与历史检索并发评估。AI 能力上线后，跨地域调用推理请求会额外占用链路，应在第三期重新评估。

### （八）直连态的适用范围与不跨网段的原因

上一版曾提出"由本地服务器兼作发现节点"来解决跨网段发现。**经确认，该方案不再需要，本节说明理由与由此确立的边界。**

**定位。** 免登录直连态要解决的是"临时、就近、零部署"这一类需求——访客临时接入、临时借用一台机器、同一办公区域内即刻沟通。这类场景的共同特点是发生在本网段之内，且是短时的。用户对此的表述是"本来就是暂时使用一下"。**"暂时"与"就近"两个词，就是直连态的完整边界。**

**三条不做跨网段的理由。**

其一，**做了就守不住定位。** 一旦为跨网段发现投入工作——无论是请网络管理员配置 UDP 中继，还是部署发现节点——直连态就不再是"零部署、装完即用"，其核心价值随之消失。到那时它与一套需要规划、需要协调、需要维护的系统并无区别，反不如直接登录。

其二，**协作态已经覆盖这类需求，而且更省事。** 跨网段与跨地域沟通，登录后天然可达，不需要任何网络改造（详见表 20）。既然协作态在这些场景下体验更好、能力更强（有历史、有组织架构、有检索），就没有必要让直连态去追平它。

其三，**合规上更干净。** 直连态消息不经服务端、不留痕。若允许它跨网段、跨地域工作，等于在企业内网中存在一条不受管控、可跨越任意网段的通信通道，等保与审计上难以解释。把适用范围收在本网段，反而是一道更清晰的边界。

**由此确立的边界。**

**直连态即本网段内的临时使用。** 它依赖 UDP 广播发现同网段设备，而广播不出网段，因此不需要、也不应为它做任何跨网段的配置或开发。**跨网段与跨地域的一切沟通，请登录协作态。**

**不保留的能力。** 上一版曾考虑由使用者手工填写对端地址或进行网段扫描以实现跨网段直连。既然定位已收敛，此项**不再保留**——留着它会把一个应急工具包装成"跨网段方案"，与定位相悖，还会引入"为什么他能跨网段、我不能"的解释成本。**确有跨网段需求时，请使用协作态。**

### （九）多地域下的文件共享

共享空间（Samba 与 Web 文件平台）建议**每地域各部署一套本地实例**，不做跨地域统一。理由是 Samba 的目录访问对时延敏感，跨城访问会明显卡顿；跨地域存储统一还会带来备份与容灾的额外复杂度。

跨地域取用文件有两种做法。其一，若地域间专线三层可达，客户端可经专线直接访问对端共享目录，适合小文件与低频访问。其二，**推荐做法是设置文件中转区**——将文件放入本域共享目录后，通过消息发送访问链接，由接收方在本地拉取，避免大文件占用跨地域链路。

## 九、风险与合规提示

本章按风险类别给出提示与应对措施，依次说明身份与接入、归档完整性、合规、可用性与技术五类风险，其中可用性与技术两类在多地域环境下有新增内容。

### （一）身份与接入风险

**风险描述：** 直连态下不存在登录凭据，任何能接入内网的终端都可直接加入通信。管理员在后台看到的是设备列表而非人员名单，一台设备由谁使用，系统层面无法确认。若开放免登录使用，员工可能长期以直连态使用而不登录，导致设备台账与人员信息的对应关系长期不完整。

**应对措施：**

第一，**启用新设备审批。** 设备首次注册后进入待审批状态，审批通过前无法登录协作态。这一开关将"接入即合法"变为"审批后才合法"，投入最小、效果最明显。

第二，**配合网络层准入控制。** 在交换机侧实施 IP 与 MAC 地址绑定，或启用端口级准入认证。此措施需网络管理员配合，建议列为前置条件。

第三，**建立设备台账与责任人登记制度。** 每台设备在审批时登记使用人、部门与责任人；人员离岗或设备退役时同步解绑停用。

第四，**设置登录引导与归属提醒。** 客户端在未登录状态下持续提示登录入口；后台对连续多日未登录的设备标记为"待归属"，由管理员推动完成绑定。

### （二）归档完整性风险

**风险描述：** 跨态会话不经服务端，直连态消息完全不进入归档，因此理论上存在规避路径——员工可与同事约定"你退出登录，我们用直连通道聊"。这不是理论推演，而是此类双态设计在真实环境中必然会被尝试的做法。

**应对措施：** 其一，提供"允许与未登录设备通信"策略开关，对归档要求高的部门直接关闭；其二，客户端在跨态会话上固定显示"未归档"标记，并上报跨态会话的建立日志（时间、双方、时长，不含内容），使异常频繁的跨态通信可被察觉；其三，在制度层面如实告知留档边界。

**这一项风险的敞口范围是明确且有界的。** 通常会被想到的另外几条规避路径，均已在设计层面封堵：撤回不抹除归档、终端侧删除不影响服务端、系统不提供面向使用者的留痕开关（逐条见第一章第二节）。因此需要管理层知情的只有一项——**跨态会话是本方案唯一存在的留痕缺口，且其成因是形态边界，不是功能设计上的取舍。**

### （三）合规风险

**风险描述：** 本方案的归档范围为"协作态会话"，即员工登录之后产生的、经服务端中转的消息。相较于全部消息归档，本方案留档范围更窄、侵入性更低，但仍有若干合规要点。

**应对措施：**

第一，**事前告知并取得同意。** 上线前通过员工手册修订或专项告知，明确说明消息留存范围、目的、期限与查阅权限，并留存告知记录。**特别需要明确告知留档边界**——哪些对话会被留存、哪些不会。

第二，**限定留存范围。** 仅留存文本消息与文件传输元数据，不抓取终端本地文件内容，不做屏幕记录，不采集与留存目的无关的信息。文件本体默认不归档。

第三，**设定留存期限并到期清理。** 建议留存期 6 个月，到期自动归档或清理。

第四，**严格限定查阅权限。** 后台查阅权限仅授予必要岗位，查阅行为本身记录日志、可追溯；查阅他人会话建议需审批。

第五，**AI 能力上线时补充告知。** 第三期 AI 能力会读取归档消息，需补充告知 AI 的读取范围与产出物处理方式。**若本单位涉及涉密等级，模型网关的外部 API 端点应一律禁止注册**；即便不涉密，归档数据也仅允许由本地模型处理（见第六章第五节）。模型网关的全部对外连接须留日志并可审计。

第六，**主动澄清并处理员工的预期落差。** 当前使用的局域网工具对外宣称"聊天记录只存本机、不经过服务器"，并配有"密聊"（阅后即焚）模式；员工对"聊天不会被公司看到"已形成稳定预期。而本方案上线后协作态消息将集中留存——**这是本项目在推行阶段最容易引发抵触的一点**，与技术方案无关，但会直接影响落地效果。

**此处需要先澄清一点，避免告知材料写反：密聊与阅后即焚是当前工具的功能，不是本方案要建设的能力。** 本方案明确不提供这类功能（清单见第一章第二节与第二章第二节）。告知材料与培训中不应把它作为"新工具的功能"来介绍，否则会在员工中造成第二重误解——以为新工具也有不留痕的选项，实际使用时才发现没有。

建议在上线前把两件事分开讲清：**免登录直连态保持"不经服务器、不留档"的原有体验**（这是该形态的固有属性，也是双引擎设计的价值之一，而非一项可供选择的隐私开关）；**登录协作态则明确告知会留存**，并在界面上以归档状态标识呈现。让员工清楚知道自己在哪种状态下说话、这句话会不会被留存，比笼统宣布"公司要开始留档了"更容易被接受。

同时应明确一条纪律并写入告知材料：**留存不等于上级可以查看下属会话。** 归档查询权限仅授予指定的管理岗位，直属上级不因"是领导"而自动获得查阅下属会话的权限。这一点若不说清，会被普遍误解为"领导能看我聊天"，成为推行的主要阻力来源。

### （四）远程协助与场所信息的两项边界

本版新增的功能中，有两项的风险性质与其余功能不同，需单独设定边界。

**其一，远程协助。** 本系统其余功能都属于"数据流动"——消息、文件、组织信息在系统内流转，风险是泄露。远程协助是**跨终端的操作权限**，风险是被滥用后可以操作他人的计算机。二者量级不在同一层次。

除第二章第四节列出的四条硬性要求（受控方显式确认、过程持续可见、全程留痕、范围可控）之外，还应在制度层面明确三件事。第一，**用途限定为故障排除与技术支援**，不得用于查看他人工作内容。第二，**留存期与查阅规则**参照归档消息（建议 6 个月），录制文件与访问记录同等保管。第三，**异常行为告警**——对非常用发起人、非工作时间发起、对同一受控方频繁连接等模式产生告警，而非仅被动留痕。

需要特别说明一点：**远程协助的留痕与管理员的归档查询是两件事，不能相互替代。** 归档查询看的是聊天内容，远程协助记录看的是操作行为。在合规审查中，后者往往比前者更需要"可举证"。
还有一点需要与留痕原则对齐：**远程协助与音视频通话的媒体内容不落地存储，但通信事实本身必须归档。** 这与文件通道的处理完全同构——保存的是“谁在什么时间与谁进行了何种性质的通信”这组元数据（参与方、起止时间、时长、连接方式），而非画面本身。远程协助的屏幕录制另设可选开关并按部门下发。媒体内容不存储是出于存储与带宽的现实约束，**不是留痕原则的例外**，两者的口径应在告知材料中一并说明，避免被理解为存在一处“不留痕的口子”。

**其二，办公室位置图。** 楼层平面图包含办公区布局、安防通道、关键设备间与机房位置。它对本系统全员可见时，等同于一份内部场所分布资料。

建议设定三条边界。第一，**仅开放本人所在楼层**，跨楼层与跨园区按需授权。第二，**安保、机要、财务、人事等岗位所在楼层**的平面图可整体不发布。第三，**平面图不做原图下发**，客户端只渲染不提供下载。位置图的可见范围宜与门禁权限保持大体一致——门禁进不去的区域，图上也不必标注。

### （五）可用性风险

**风险说明：** 本版采用双引擎设计，服务端故障时协作态的归档、组织架构与云端历史不可用，但**直连引擎仍可工作**，员工在同网段内仍能收发消息与传输文件。服务端是归档与管理能力的单点，而非通信能力的单点。这一特性应向评审组说明，它降低了服务端高可用的紧迫程度，但归档数据的丢失风险仍需通过备份对冲。**在多地域环境下，跨地域专线中断还会使该地域的协作态整体不可用**，此时该地域员工仅能依靠本网段直连沟通，跨地域消息暂不可达，恢复后按第八章第五节的规则补传归档。

**应对措施：** 数据库定期备份并验证恢复流程；准备冷备机与切换预案；公示维护窗口；客户端在服务端不可达时明确提示并说明当前已回落至直连态、消息不会进入归档。

## 十、实施计划与建议

本章给出第一期实施的阶段计划、试点建议与验收标准，并说明各阶段之间的依赖关系与外部前置条件。

### （一）总体计划

**表 24　第一期实施阶段计划**

| 阶段 | 时间 | 主要工作 | 交付物 |
| --- | --- | --- | --- |

| 第二阶段：直连态试点 | 第 3–4 周 | 选择 1 个部门试点，验证同网段发现成功率、大文件速率、双态切换 | 试点记录与问题清单 |
| 第三阶段：服务端与协作态 | 第 5–8 周 | 接入网关、账号与设备、组织架构、消息归档、多端登录管控、客户端登录与切换 | 具备归档能力的完整系统 |
| 第四阶段：管理后台与策略 | 第 9–10 周 | 成员与部门管理、权限、设备台账、登录记录、消息检索导出、各项策略开关 | 可管理的系统 |
| 第五阶段：体验功能与跨态 | 第 11–12 周 | 截图与标注、表情包、常用联系人、汇报关系与通讯录可见性；跨态识别与路由、归档状态标识；部署共享空间并衔接权限 | 双态完整形态 |
| 第六阶段：全面推广与验收 | 第 13–14 周 | 总部地域分批铺开、台账登记与培训；按验收标准逐项确认 | 验收报告 |
| 第七阶段：跨地域推广 | 第一期验收后 | 核验网络侧前置条件、各地域经专线接入、分域铺开与培训 | 异地地域上线 |

四点需要说明。第一，**第一阶段不含任何服务端工作**，不受服务器采购与网络改造进度影响，可立即启动，这是分期方案的主要价值。第二，**网络层准入控制、服务端采购与跨地域专线改造的进度决定第三阶段能否按期开始**，应在第一阶段同期启动评估；其中跨地域专线改造由网络管理员负责，周期通常长于软件开发，建议最早启动。第三，**汇报关系数据的准备可与开发并行**——成员与直属上级的对应关系若由管理后台手工维护，需人事部门在第一期开发期间同步整理；若改由 HR 系统同步，则需额外的协调与工期，应尽早确定（见第十一章决策事项）。第四，第二期与第三期应在第一期验收通过后单独立项，各期边界独立、成果独立验收。

### （二）试点建议

试点部门建议选择人数适中、终端类型覆盖全面（同时包含 Windows 与国产系统）、且有兼职 IT 联络人的部门。规模不宜超过 20 台终端，目的是在低成本前提下暴露设备发现、文件传输、大文件性能与双态切换四类问题。试点期间应重点验证：UDP 广播在实际网络中的**同网段**发现成功率、大文件在千兆网络中的实际速率、登录后组织架构与历史检索的响应速度。**同时应在试点中确认一件事：试点部门的终端是否处于同一 VLAN。** 若办公区已按楼层或部门划分多个 VLAN，直连态在部门内部也可能互相发现不到——这不是缺陷，但必须在推广前摸清，以便在培训中提前说明、避免被当成故障。多地域环境下建议在第二轮试点中选取一个异地分部，重点验证专线时延、跨域消息可达性与历史检索的响应速度。

## 附录 A　设备指纹实现要点

**表 A-1　硬件信息采集项**

| 采集项 | Windows 取值方式 | Linux 取值方式 | 是否计入指纹 |
| --- | --- | --- | --- |
| 主板 UUID | Win32_ComputerSystemProduct 的 UUID 字段 | /sys/class/dmi/id/product_uuid | 计入（主） |
| CPU 标识 | Win32_Processor 的 ProcessorId 字段 | /proc/cpuinfo 中的序列号字段 | 计入（主） |
| 系统盘序列号 | Win32_DiskDrive 的 SerialNumber 字段 | /sys/block 下对应磁盘的 serial | 计入（辅） |
| 网卡 MAC | Win32_NetworkAdapter 中仅物理网卡 | 网络接口硬件地址 | 不计入，仅作参考 |

实现要点如下。

一，**排除虚拟网卡。** 采集网卡信息时须过滤虚拟化软件与 VPN 客户端创建的虚拟适配器，仅保留物理网卡。

二，**主辅分级。** 主板 UUID 与 CPU 标识作为主指纹，系统盘序列号作为辅助校验，三项中匹配两项即认定为同一设备，以容忍单次硬件维修。

三，**敏感项不参与。** 内存容量、操作系统版本、设备名称等易变项一律不参与指纹计算。

四，**指纹只存哈希。** 服务端仅存储指纹的 SHA-256 哈希值，不存储原始硬件信息。

五，**用途界定。** 指纹用于直连态身份标识、设备台账与登录记录三处；**不承担限制登录的职责**——账号可在不同设备登录，管控通过"桌面端单点在线"与"新设备登录审批"实现，而非绑定硬件。

六，**失效与重注册。** 重装系统或更换主板、系统盘会导致指纹变化，设备将被识别为新设备，需管理员审批后使用。由于不影响换机登录，此类情况不会阻断员工正常工作。
