# 信箱：统一收件箱（设计稿，未实施）

> 状态：设计稿（2026-10-12 用户拍板「按本稿方案做」），本轮只出设计不改代码，
> 等用户过目后再排实施。一句话：**一个入口收三类条目（警告＋通知＋公告）**。
> 用词只用现成词（信箱/警告/通知/公告/已读/回执），不造新概念。

## 一、一个入口，三类条目

| 类目 | 收什么 | 来源（复用，不新建） | 提醒与状态 |
|---|---|---|---|
| **警告** | 服务端健康/磁盘/备份失败/登录异常等系统侧事件；机器人经 webhook 上报的异常 | admin 事件源（P3 打通，见§五）＋webhook 入口 | 强提醒＋未读常驻红点＋**可标已处理**（处理动作与处理人留痕） |
| **通知** | @我、任务到期、审批结果、共享变更 | 通知中心（任务提醒 30s 轮询到期待办）、审批通知经通知中心（todo 审批线 2026-10-08 第一笔）、@我与会话面既有口径 | 强提醒＋回执**只提醒一次**，沿用现有口径（T4.10 通知子系统三级分级＋个人通知偏好 notify_prefs） |
| **公告** | 部门或全员广播（即 R24 群组知识共享里的公告） | R24 公告（群公告 R24-1 已闭，部门/全员广播形态为其扩展） | 弱提醒＋**已读确认留痕**（谁/何时确认落库可查） |

三类条目共用一张收件箱视图；条目本体留在各自来源，信箱只管「进箱、
未读、已读、已处理」（§二边界①）。

## 二、三条硬边界

1. **信箱＝视图＋已读状态，不是新通道。** 复用通知中心、webhook、admin
   事件源、R24 公告等既有来源，**禁止建第三套推送链路**——信箱面只新增
   「条目状态」（未读/已读/已处理，按账号逐条），不搬数据本体、不复制
   消息内容。
2. **「清空/标已读」只动信箱状态，绝不动归档。** 留痕原则铁律（todo §零）
   与 R3 验收口径（不提供任何可由发送方消除已归档内容的功能）优先级最
   高：信箱里删除/清空＝从我的视图移除＋状态留痕，消息归档行、公告行、
   警告台账行一律不动，任何信箱操作不得触碰归档。
3. **三端同源。** 桌面/手机/admin 读同一份服务端条目状态；手机横幅点进
   同一信箱；**未读计数单一来源在服务端**，三端展示同一计数，不许出现
   两套未读数。

## 三、版式定案（用户 2026-10-12 拍板）

默认**一个收件箱＋类型筛选**（警告/通知/公告三个筛选片），**不拆
「与我相关/全局广播」两栏**——拆两栏手机端就多一个入口，违背三端同源
的最小入口口径。

## 四、分期与可测验收

| 期 | 内容 | 可测验收 |
|---|---|---|
| **P1** | 箱视图＋未读计数＋标记已读：服务端条目状态面（按账号逐条未读/已读），桌面收件箱视图＋类型筛选 | 三类条目各造一条均进箱；未读计数跨重启正确（服务端为准）；标已读后计数递减且归档行数不变（R3 断言）；警告可标已处理且处理人留痕 |
| **P2** | 公告已读确认留痕＋通知回执与现有提醒策略合并：公告确认（谁/何时）落库可查；回执只提醒一次口径并入 T4.10 分级 | 同一通知重复刷新不重复弹（只提醒一次断言）；公告已读确认留痕可按人/按条目查；提醒行为与 notify_prefs 现有开关一致（无第二套开关） |
| **P3** | 打通 admin 系统警告源：服务端健康/磁盘/备份失败/登录异常进警告类目；webhook 机器人上报进警告 | 造磁盘满/备份失败事件→警告进箱＋红点常驻直至已处理；登录异常（连续口令不符）进警告；非管理员默认看不到系统细节（拍板项②口径） |
