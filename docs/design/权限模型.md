# 权限模型：用户-群-角色-授权（横切设计）

> 状态：设计稿（2026-10-04 用户定调：「类似 Linux 的账号管理」）。定位：R23-R26 共用的统一权限模型——群=组、入群即继承、建群需特权、群能力由管理员配置。互引：群工具框架（R25）、群服务器工具（R26）、群组知识共享（R24）、组织架构（群在组织架构中可见）。
>
> **实现状态（2026-10-08 对账，二批收口）**：模型六规则全数落地——群内角色（群主/管理员/成员）与「入群即继承、退群即失」随 R23-2 落地（`group_members.role`＋AuthorizationService 策略注册）；「建群需授权」随平台-12 落地（202d626：CollabServer group_az_ 判权，追加角色 `group_creator`（org role grant，时间窗机制）或基础 admin 放行，未授权默认拒）；「群能力管理员配全」随平台-12 建立表与词汇表（`group_capabilities` 七项：notice/memo/vault/tools/server_tools/files/uplink；未配置=现行允许、配置禁即拒——首段步进口径，全面 deny-by-default 留后续）＋变更台账＋CLI `group capability set|list`；「群在组织架构可见」与「R24-R26 各面按模型统一接线」随二批收口落地：ORG_DATA 携 `OrgGroup` 全量群下发（/etc/group 类比，透明可查不按查看者裁剪）、客户端组织架构树列群组成员，FileServer `capability_gate` 统一门铺满 memo/vault/tools（含 ci/pack/export）/server_tools 四面 37 路由＋files 面四动词（upload/list/download/pin/delete），停用即 403 `deny:capability-<名>`；「全程留痕」=建群拒/授/能力变更均落台账。词汇表 uplink 项暂无执行点（现外网收件箱面按账号无群维度，群收件箱面落地时随接）。

> **冲突与继承（2026-10-10，计划书§八收口）**：档序 Explicit Deny > Explicit Allow > Inherited > Default Deny 写死进引擎与本文档§5；作用域（Scope）维度落地——`add_scoped_rule` 挂部门路径、查询携 `scope`、链上才可命中、同档内最近作用域优先（同深同档先注册先匹配），存量全局规则行为不变。

## 1. 模型（Linux 组模型 + 群内角色 + 留痕）

```
用户(User) ──加入──► 群(Group，权限载体) ──配置──► 授权面(工具/资源/动作白名单)
                        │
                        └─ 群内角色：群主 / 管理员 / 成员
```

| 规则 | 内容 | Linux 类比 |
|---|---|---|
| 入群即继承 | 群配好的工具/资源能力，成员自动获得 | `usermod -G` 继承组权限 |
| 退群即失 | 退出/移除即刻回收 | 移出组 |
| 建群需授权 | 创建群是特权动作（组织架构管理员授予或审批） | `groupadd` 需特权 |
| 群能力管理员配全 | 该群用哪些工具（CI/CD/服务器/文件/密码箱…）由管理员勾配 | 组 ACL/sudoers |
| 群在组织架构可见 | 所有群进组织架构树（透明可查） | `/etc/group` |
| 全程留痕 | 谁行使了什么能力全记录 | （Linux 无此层） |

## 2. 群内角色（比 Linux 多的一层）

- **群主**：群的拥有者（配置工具、任免管理员、转让/解散）；
- **管理员**：工具配置、成员管理、公告/备忘录维护；
- **成员**：使用群已配的能力。

角色是群内分层，不跨群（一个用户在 A 群是管理员、B 群是成员，互不影响）。

## 3. 授权面（管理员「配置全」的清单）

一个群的能力开关（管理员勾选）：群公告 / 群备忘录 / 群密码箱 / 群工具（CI/CD、打包、配置导出…）/ 群服务器工具 / 群文件 / 外网上传收件箱。每个能力可再带细粒度白名单（如 CI/CD 只允许触发哪些 pipeline）。

## 4. 边界

- 组织架构管理（建组织/部门、授权谁能建群）归组织管理面（memex 已有组织架构，本模型只定义群与权限关系）；
- 凭据（密码箱/服务器凭据/工具 token）永不因「入群」而明文可见——**权限=可行使动作，凭据仍走加密面+显式解锁**。

## 5. 冲突与继承（计划书§八，2026-10-10 落地）

**档序写死（全局优先，与深度无关）**：

1. **Explicit Deny**（显式拒绝，压过一切 Allow）；
2. **Explicit Allow**（显式允许：属主、群主/管理员管理权）；
3. **Inherited**（继承允许：群成员既定能力）；
4. **Default Deny**（白名单口径：无任何规则命中即拒）。

**作用域（Scope）维度**：规则可挂部门路径作用域（如 `公司/技术中心/游戏部`），查询携带同一作用域。规则作用域**在查询链上**（等于该路径，或查询路径以其＋`/`前缀开头的下级）才可能命中；离链不命中。无作用域规则＝全局，恒覆盖。

**同档内解近**：同一档命中多条时取**最近作用域**（路径段数最深者）；同深同档取**先注册**先匹配（确定性）。档间次序不受作用域影响——挂在最深作用域的 Deny 照样压过挂在浅层的 Allow。查询无作用域时仅全局规则可命中。

**既有执行点**：

- 部门链逐级上溯的策略解析（`resolve_policy` / `assist_policy_resolve`：本人部门→逐级上级→全局行→内置默认）与本引擎同向——最近作用域优先；
- 数据过滤（蓝图§七）与单点裁决同源：`filter_allowed` 对查询结果集逐条过同一规则桶，不该见的行在服务端滤掉而非 UI 隐藏；
- 理由留痕口径不变：`deny:<名>` / `allow:<名>` / `inherited:<名>` / `default-deny`，审计据此回答「谁被允许/拒绝、依据哪条规则」。
