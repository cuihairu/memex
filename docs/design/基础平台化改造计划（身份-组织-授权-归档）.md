Identity

name
status

### Device

device_id
device_fingerprint
device_type
os

### Session

session_id

## 三、第二优先级：Authorization 正式独立

现状（部门、成员、角色、权限、通讯录可见性、策略、会话审计、位置图、远程协助）比较像「各功能自己的权限要求」。升级为：

```text
Authorization
│
├── Permission
├── Role
├── Scope
├── Policy
└── Decision
```

不只做传统 RBAC。

### 1. Permission：能做什么

```text
user.read / user.update
department.read / department.manage
message.search / message.export / message.audit
device.read / device.manage / device.kick
file.read / file.write / file.share
remote_assist.request / remote_assist.control
location.read / location.manage
policy.read / policy.update
```

### 2. Role：谁可以做什么

```text
Employee
IT
HR
DepartmentAdmin
SecurityAuditor
SystemAdmin
```

角色只是 Permission 的集合。

---

## 四、最重要：Scope

权限不是简单 `can message.search = true`，而是 `can message.search WHERE department = X`：

```text
SELF
DEPARTMENT
DEPARTMENT_AND_CHILDREN
ORGANIZATION
SPECIFIC_USERS
SPECIFIC_DEPARTMENTS
```

示例：HR → `user.read` + scope=HR_DEPARTMENT；IT → `device.manage` + scope=ALL；审计员 → `message.search` + scope=AUTHORIZED_DEPARTMENTS。

---

## 五、Policy

Permission 与 Policy 分开：

```text
Permission: remote_assist.control      → 具有远程协助能力
Policy: remote_assist                 → 在什么条件下才能使用
    allowed_department = IT
    require_consent = true
    require_audit = true
    record_screen = optional
```

（文档已明确远程协助需「显式授权、持续可见、全程留痕」；位置图、跨态通信、新设备登录等也有策略控制。）

**Authorization Decision 流程：**

```text
Subject → Role → Permission → Scope → Policy → Resource → Allow / Deny
```

---

## 六、权限决策必须是统一服务

禁止 `if (user.department == ...)` 散落在 org/archive/file/location/remote/admin 各处：

```text
AuthorizationService.authorize(subject, action, resource, context)
→ ALLOW / DENY
→ 附 reason, matched_policy, scope
```

这样审计才能回答「为什么这个人能看到这条消息」。

---

## 七、权限必须支持「数据过滤」，不仅是操作权限

通讯录「不可见 + 不可搜索」不能只在 UI 层 `if (!visible) hide()`，必须在数据访问层：

```text
Server Query → Authorization Filter → Allowed Records → Client
```

否则搜索 API 仍可能返回隐藏用户。**授权必须在数据访问层生效，不是只在 UI 层。**

---

## 八、权限继承与冲突规则

多层结构（公司→技术中心→游戏部/基础设施部）下「公司允许/技术中心允许/游戏部禁止」的裁决优先序必须写死：

```text
Explicit Deny > Explicit Allow > Inherited Policy > Default
```

或更简单：「默认拒绝 + 最近作用域优先」。**必须写进设计文档**，否则权限一复杂就失控。

---

## 九、策略不是「部门开关」大杂烩

统一 Policy 结构：

```text
Policy
{
    resource
    action
    subject_scope
    condition
    effect
    priority
    effective_at
    expire_at
}
```

现有 `policies(department_id, policy_item, value)` 逐渐升级，避免变成 key/value 大杂烩。

## 十、双引擎设计保留并强化

```text
                 Memex Client
                      │
       ┌──────────────┴──────────────┐
       │                             │
 Direct Engine                Collaboration Engine
       │                             │
 UDP Discovery                   Gateway
 TCP P2P                         Account

```

**不要把两个 Engine 合并成一个 Transport。**（保持现状取舍。）

## 十一、修改一个重要行为：不要「静默降级」

服务端不可达自动回落直连态，从可用性角度好，但从留痕角度危险：

> 用户以为还在登录归档，实际服务端挂了自动 Direct、消息不归档——认知风险。

必须显式显示「当前处于未归档通信状态」，且统一覆盖：

```text
顶部状态栏 / 会话标记 / 输入框提示 / 发送前状态 / 恢复后的补传规则
```

--- 

## 十二、跨态通信定义为「显式风险域」

```text
Communication Domain
ARCHIVED        （归档）
UNARCHIVED      （未登录直连，不归档——现设计保留）
DEGRADED        （本应归档但服务端不可达，降级不归档——必须显式标识）
```

不是简单的 online/offline。

---

## 十三、归档模型：Event Sourcing 风格不可变记录

现有「撤回不删服务端原文、只加撤回事件」方向正确，统一为：

```text
Message             （原始消息 immutable）
MessageEvent        （append-only：message.created / delivered / read / recalled / edited）
Current Message State（可由事件重建）
```

审计、撤回、编辑、送达、已读、导出都受益。

---

## 十四、「永久留存」决策要重新定

decisions.md 出现矛盾：报告建议 6 个月，工程口径变成「永久留存、清理可配」。

改口径：**不可由普通用户删除；最终生命周期由管理员配置。**

```text
Retention Policy
├── 30 days
├── 6 months
├── 1 year
├── 3 years
└── Indefinite
```

「不可篡改」与「合法生命周期管理」不冲突。

---

## 十五、管理员也不能「无痕删除」

Admin Delete 必须变成 Retention Purge，并记录 who/when/what/why/policy/approval：

```text
High Risk Operation → Two Person Approval → Purge → Audit Event
```

message export / message purge / audit access / remote control / policy change 均属高风险操作。

## 十六、会话审计权限独立于普通管理员权限

```text
SystemAdmin     system.manage, device.manage    （≠ 自动可读消息）
SecurityAuditor message.audit, message.search, message.export
DepartmentAdmin user.manage, department.manage
```

禁止 `Admin = 可以看所有聊天`。

## 十七、审计本身也需要审计

```text
Auditor A → 查询员工 B → 查看 2026-10-01 消息
→ 生成 audit.message.search / audit.message.view / audit.message.export
```

```text
业务数据 → 审计 → 审计日志（本身不可被普通管理员修改）
```

否则「管理员查员工聊天」本身就是黑箱。

## 十八、文件系统区分两个概念

```text
File Transfer    = message attachment / temporary transfer（客户端文件柜＝快速传递）
File Space       = persistent collaborative storage（集中共享文件平台，第二期独立）
```

不要让两者混成一个 File。

---

## 十九、文件旁路必须加「传输授权」

```text
Server ── metadata      A ──────── B（bytes 不过服务端——保留）
```

但必须解决：A 有没有权限发？B 有没有权限收/下载？文件是否允许跨部门？是否允许再转发？

**FileAuthorization 必须调用统一 Authorization Service**——文件不经服务器，但权限不能绕开服务器。

---

## 二十、P2P 不能因为是内网就默认「可信」

UDP 广播发现 + TCP P2P 意味着「能进同一二层网络 ≠ 可信用户」。至少加入：

```text
Device Identity + Authenticated Handshake + Session Key + Message Integrity
```

UDP 广播本身不承担身份认证：

```text
UDP Discovery only → TCP → Cryptographic Handshake → Authenticated P2P Session
```

---

## 二十一、Direct Engine 明确加密边界

```text
Discovery: device_id / public_key / capabilities
→ X25519 Session Key → AEAD → Message / File
```

局域网抓包不能直接读聊天内容。

---

## 二十二、消息协议提前定 ID / ACK / 幂等

```text
message_id
conversation_id
sender_id
client_sequence
server_sequence
created_at
```

投递语义：at-most-once / at-least-once，**实际推荐「客户端至少一次发送 + 服务端 message_id 幂等去重」**，不追求网络层 exactly once。

## 二十三、客户端本地库正式设计 Sync State

`source + sync_state` 承载过多语义，升级为显式状态机：

```text
LOCAL / PENDING / SENDING / SERVER_ACKED / ARCHIVED / FAILED
+ archive_state
```

Account

## 二十五、直属上级独立字段保留

**直属上级不能由部门结构推导**——Department Tree 与 Reporting Line 是两个不同的图，不能混为一个树。

## 二十六、位置图权限不只是「部门可见」

位置图是敏感空间信息：

```text
Location: Visibility / Accuracy / Role / Purpose
```

普通员工见同部门、IT 见全楼、HR 见组织范围；甚至「只显示姓名、不显示精确座位」。不要变成企业内部实时定位系统。

## 二十七、远程协助设计成独立 Security Domain

现有原则（显式确认、持续可见、全程留痕、范围可控）保留，模型：

```text
RemoteAssistSession
{
    id, requester, target
    requested_at, approved_at, started_at, ended_at
    permissions: view / keyboard / mouse / clipboard / file_transfer
    consent, audit
}
```

而不是一个 `remote_control = true`。

## 二十八、AI 的权限：正式复用 Authorization

V10 已正确（AI 读取消息携带调用者身份，不因 AI 是服务绕过用户权限）。升格为系统原则：

```text
AI is a user of Memex
User → Authorization → AI Service → Retrieval
```

而不是 `AI Service → Database → Everything`。

## 核心原则（取代「连接服务端的唯一目的即留痕」）

> **通信、身份、权限与留痕必须始终可解释。**

1. **Direct First**：没有服务端也可以在局域网完成基本通信。
2. **Server Collaboration**：服务端提供身份、组织、协作、跨网段通信和归档能力。
3. **Authorization Everywhere**：所有受保护的数据与操作都必须经过统一授权，而不是由业务模块自行判断。
4. **Audit by Design**：归档、撤回、查询、导出、权限变更、远程协助等高风险行为都必须产生可追溯记录。

**最优先执行的唯一改动**：

> 把 **Authorization** 从 `org` / `policy` 中抽出来，成为和 Identity、Organization、Archive 同等级的核心 Domain，而且第一期就完成基础框架。

理由：双引擎设计已成熟、归档原则明确，真正缺一根贯穿所有功能的骨架——统一授权模型。骨架补上后，通讯录、文件、审计、位置图、远程协助、AI 都能自然挂上去。
