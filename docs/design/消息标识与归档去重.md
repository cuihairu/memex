# 消息标识与归档去重设计（BUG-007 整体设计稿）

> 状态：设计稿（2026-10-10，BUGS.md BUG-007 登记口径「只登记不修、须整体设计」的交付物）。**未动码、待授权**——本稿只定方案，动手实现须用户另批授权（届时按 §5 分批，每批测试绿才提交）。互引：BUGS.md BUG-007（现象与定位原话）、T2.2（消息标识去重）、T2.3（归档）、T2.5（断线补传）、平台-9（Sync State 与 seq 续位）。

## 0. 根因与碰撞向量全集

现行 msg_id＝`sha256(from + ":" + seq)`（session.cpp TEXT/NUDGE 两处），而 (from, seq) 不唯一标识一条消息。碰撞向量四个：

| # | 向量 | 现状 |
| --- | --- | --- |
| V1 | 同账号同设备重登，seq 每连接重置（Android／iOS／鸿蒙 seqGen 均为会话实例字段） | 2026-10-09 两起走查实录坐实（归档吞行） |
| V2 | 同账号跨设备并存（T2.1 跨类型并存：桌面＋手机同在线），各设备独立 seq 计数，同 seq 即撞 | 未爆发，同根因 |
| V3 | 新设备／清数据首登 seq 从 1 起，与同账号任意历史消息撞（桌面平台-9 只保同设备续位，新装机无历史可续） | 未爆发，同根因 |
| V4 | seq 回绕 | uint64 理论项，不计 |

后果链：服务端归档 `INSERT OR IGNORE` 静默吞行（审计／漫游／检索失真，留痕原则受损）＋发送方 ACK 照回（受理假象）；**投递面不受影响**（在线即投不走归档判重，离线槽被消费后可再入队）。桌面端另有一层：本地库 `UNIQUE(from_id, seq)`（local_store.cpp:72）使接收端对重用 seq 的新消息同样本地不可见——服务端已归档、ACK 已回，本端列表永远缺行。

## 1. 设计面事实（代码实证，2026-10-10 采集）

- **msg_id 生成点三处**：TEXT（session.cpp:201）与 NUDGE（session.cpp:659）＝sha256(from:seq)（碰撞面）；NOTICE（webhook.cpp:477）＝sha256(sender:target:ts:随机盐)（服务端发起，天然不撞，不在碰撞面）。
- **发送侧对派生式有依赖**：桌面客户端发出即本地派生同式 msg_id（collab_engine derive_msg_id，需求批⑦），送达／已读回执、撤回（recall.msg_id）、已读上报全按它命中本地行。
- **补传幂等是现行派生式的偶然性质**：桌面 T2.5 补传按原 seq 原 ts_ms 重建帧（flush_pending_sends），全链依赖「同 (from,seq)→同 msg_id→INSERT OR IGNORE 幂等」；任何改法必须保留该性质。
- **接收端去重键已分叉**：桌面本地库双键 UNIQUE(from_id,seq)＋msg_id 部分唯一索引；Android／iOS／鸿蒙按 msg_id 去重。
- **ACK 两向**：发送方受理 ACK(seq)（无条件回）；接收方 ACK(msg_id) 清 offline_messages（UNIQUE(msg_id,to_account)，blob 存最终帧）。
- **seq 生命周期**：桌面＝登录后从本地库续位（next_local_seq，平台-9）；Android（ChatSession.kt:81）／iOS（ChatSession.swift:49）／鸿蒙（session.ts:65）＝每连接重置——V1 主犯。
- **messages 表无 seq 列**，msg_id UNIQUE；store_message 的 bool 返回值在 session.cpp 两处均被忽略（即缺陷本体）。

## 2. 方向取舍：两条直觉修法为何都不完备

**纯 A（服务端一律发唯一 msg_id，单调成分或时间戳）**：服务端无法区分「同 (from,seq) 的补传重发」与「重用死 seq 的新消息」——按 (from,seq) 判重则 V1/V2/V3 照吞（现状）；一律发新 id 则桌面补传每次重发多归档一行＋重投一次（违反 T2.5 验收「归档无重复无缺失」），接收端按 msg_id 去重同步失效。**A 单独不可行。**

**纯 B（客户端 seq 跨连接持久化）**：闭 V1，但 V3（新装机无历史可续）与 V2（跨设备各记各的）天然闭不了——除非服务端统一发号（协议大改）。B 只是降频，不是根治。

**结论：根因在「服务端把可能重复的 (from,seq) 当唯一键用、撞了不吭声」。完备修法必须让服务端在撞键时有分辨手段——内容比对是服务端已有的、唯一可靠的判据。**

## 3. 选定方案：撞 id 内容比对消歧＋换盐重排（服务端自主完备，零 schema 迁移）

TEXT/NUDGE 入库时（session.cpp 两处同改）：

1. 照常算 `msg_id = sha256(from:seq)`，调 store_message 并**检查返回值**；false 时先按 msg_id SELECT 既有行区分「撞键」与「库错」（库错维持现状照常受理，归档失败另有事件台账，不在本稿范围）；
2. 撞键则比对既有行 (to_account, type, text, ts_ms) 与来帧：
   - **全同 → 真·补传／超时重发**：维持现状全链（离线队列 OR-IGNORE 不重排、在线即投照发、ACK(seq) 照回）——补传幂等性质原样保留，桌面补传链零改动；
   - **有异 → 重用死 seq 的新消息（本缺陷 Case）**：换盐重排 `msg_id = sha256(from:to:ts_ms:随机盐)`，以新 id 重跑 store_message＋queue_offline＋在线投递；ACK(seq) 照回不变；
3. 群消息同路径（to=group:N 同一次入库），无需分支。

判据可靠性：真补传必同内容同 ts——桌面补传重建帧保留原 ts_ms、重发（delivery_timer_ 超时转补传）同源 PendingSend；「同发送者＋同 seq＋同毫秒＋同收件人＋同文本而实为新消息」在工程上不可区分，也不必区分——对任何可观测面它就是同一条消息。

### 3.1 msg_id 重排派生式拍板：时间戳＋随机盐（非服务端单调成分）

选**时间戳＋随机盐**（NOTICE 同式，webhook.cpp:477 先例），理由四条：

- **同域一致**：服务端已有一条 ts＋盐派生链（通知面），不新造第二套派生式；
- **零持久状态**：单调成分需独立计数行＋原子 UPSERT＋跨重启恢复；时间戳＋盐无状态；
- **单调性无人消费**：全库无任何按 msg_id 排序的路径（归档排序 id/ts_ms、离线队列按 id、回执链精确匹配）——单调性是零收益约束；
- **碰撞概率**：sha256(毫秒时戳＋64 位盐) 工程零。

### 3.2 四面联动

- **ACK**：发送方受理 ACK(seq) 不动；Ack 消息**加可选 msg_id 字段**（proto 只增不改，向后兼容）回带最终 id，桌面发送侧行的 msg_id 得以校正（§4.3）；老客户端忽略新字段无损。
- **按 msg_id 去重（接收端）**：Android／iOS／鸿蒙按 msg_id 天然兼容（重排 id 是新值不撞）；桌面本地双键中 (from_id,seq) 会拦重排行——配套回退见 §4.2。
- **归档**：撞且内容异 → 两行齐（旧行原 id、新行新 id，各自自成 message_events 事件链互不污染）；撞且内容同 → 幂等一行（现状）。检索／导出／审计零改动。
- **重投**：offline_messages blob 存最终帧（含最终 id），重投自洽；接收端 ACK(msg_id) 清队列不动；T2.5 补传命中内容比对 → 原样幂等。

## 4. 客户端同批配套

### 4.1 移动端 seq 持久化（答「是否同批」：是）

Android（per-account 落盘 seqGen、发号即写，PrefsInitStore 同款机制）／iOS／鸿蒙三端口径对齐桌面平台-9 既有行为。价值不在正确性（§3 已服务端自主完备）而在**让重排路径退化为兜底**：常规流保持 sha256(from:seq) 派生式，发送侧对派生式的既有依赖（回执／撤回命中）在绝大多数消息上不经过 ACK 校正路径。

### 4.2 桌面接收端 (from_id,seq) 拦截回退

handle_text 落库前查 (from_id,seq) 槽位：被占且既有行 msg_id ≠ 来帧 msg_id（＝重排新消息被本地拦）→ 改用 next_local_seq(from) 重存——handle_notice 对 seq=0 通知已有同款先例（collab_engine.cpp:912-915），照搬即可；msg_id 相同则照旧去重（真补投）。

### 4.3 桌面 ACK 消费

handle_ack 收到 Ack.msg_id 非空 → 更新本地行 msg_id（store 新 setter）；此后送达／已读回执、撤回按新 id 命中。老版本桌面不消费 → 撤回／回执对重排消息脱靶（服务端查无此 id 静默无操作、不留脏状态），升级窗口残差如实接受。

## 6. 验证方式（授权后随批写）

- **服务端**：①V1 重演——同账号重登发同 seq 不同内容 → 归档两行齐、新行 msg_id ≠ sha256(from:seq)、ACK(seq) 照回；②补传幂等——同 (from,seq) 同 to/text/ts 重发 → 归档仍一行、离线队列不重排、在线重投照发；③Ack.msg_id 回带腿；④群消息撞 id 腿；⑤库错（非撞键 false）受理行为不变腿。

- **移动端**：⑧各端 seq 持久化腿（重登续位断言——Android JVM 单测／iOS swift test／鸿蒙 node:test）。

## 7. 残差与如实边界

- ACK 消费部署前，旧桌面对自己发出的重排消息撤回／回执脱靶：静默无操作，不留脏状态。
- §4.2 部署前，旧桌面对接收的重排消息本地列表缺行：服务端归档可检索，本地不可见——升级窗口期残差。
- 极端同内容同毫秒同 seq 的「实为新消息」被判为补传：工程不可区分，对可观测面等价，接受。
