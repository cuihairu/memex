## 1. 多端同时在线（R4 口径）——todo.md §五「待用户拍板」①

- **推荐决策**：一期不改口径，维持「桌面端同账号单端在线互踢」；多端同时在线纳入二期（R10 功能范围参照企业微信）独立评估立项。
- **理由**：
  1. 收益：一期 R4 验收已达成（单端在线互踢＋登录记录，todo T2.1），守住口径即守住已验收交付，不引入回归。
  2. 成本：多端在线需协议＋存储＋UI 三端改动（消息状态合并、已读水位跨端对齐、归档去重），与一期交付绑死会拖累验收。
  3. 风险：已读水位需反推逐条状态，乱序已读是真实缺陷源（todo L570：逐条上报 vs 水位之争），一期强改风险集中在已验收面。
  4. 事实：R4 现为单端在线；企业微信口径为多端，差距已在 §四 如实盘点（「多端同时在线（R4 现为单端在线，与企业微信口径不同）」）。
- **立即执行动作**：记录决策，无代码动作。✅ 已执行（记录决策，commit dfd764f）
- **不做／延后**：一期不实现多端在线；二期单独立项时再评估。
- **教学**：单端在线＝同一账号同一时刻只有一台电脑能登，后登的把先登的踢下线（保证消息不错乱）；多端在线＝手机／电脑同时收消息，需要复杂的「哪台读过了」对齐逻辑，容易出错，所以放二期慢慢做。

## 2. 音视频自研还是复用内网现成组件——todo.md §五「待用户拍板」②

- **推荐决策**：复用内网现成组件，单独立项；不自研。
- **理由**：
  1. 成本：自研采集／编码／传输是重功能（todo §五：音视频是重功能）；全仓现无 VIDEO/AUDIO 帧类型（memex.proto 止于 MESSAGE_PAGE=58），从零到可用成本极高。
  2. 收益：复用现成组件（如 WebRTC 媒体底座）可较快达到可用；当前远程协助用 500ms JPEG 抓屏轮询（assist_dialog.cpp:400-412），非实时流，恰好说明自研音视频成本。
  3. 一致性：与已定案方向「音视频会议·协同文档：不自行开发、独立立项」（todo §五 第四期）一致。
  4. 风险：自研音视频的合规／带宽／兼容风险高；复用组件需先评估内网可行性。
  5. 事实：视频会议／语音通话均未实现（2026-10-15 实读：proto 无 VIDEO/VOICE，采集／传输零符号）。
- **立即执行动作**：记录决策（确认既有「不自行开发」方向），无代码动作。✅ 已执行（记录决策，commit dfd764f）
- **不做／延后**：本轮不实现音视频；单独立项时定组件选型。
- **教学**：自研视频通话＝要自己写摄像头采集、编码、网络传输、解码，是几个月的活；复用现成组件＝直接接内网已有的，又快又稳。所以选复用。

## 3. 身份源先做 LDAP/AD 还是先做 OIDC——todo.md §五「待用户拍板」③

- **推荐决策**：两案并存（不互斥）；LDAP/AD 先行（已落地），OIDC 后续独立接入（设计已备，实现排后续）。
- **理由**：
  1. 事实：LDAP/AD 可选企业身份后端已落地（todo L528-529：自写最小 BER 客户端，16 腿假目录，ctest 82/82）；OIDC 设计在写（docs/design/OIDC身份认证接入设计.md），未实现。
  2. 收益：可插拔认证后端设计本身支持并存（todo L528：可插拔认证后端）；先做已落地的 LDAP，OIDC 作为另一可插拔后端接入，不改既有信任模型。
  3. 成本：二选一反而要弃置已落地成果；并存复用统一插拔口。
  4. 风险：低——两者均 fail-closed＋组→角色显式映射（todo L528）。
- **立即执行动作**：记录决策，无代码动作。✅ 已执行（记录决策，commit dfd764f）
- **不做／延后**：不弃 LDAP；OIDC 实现按后续排期。
- **教学**：LDAP/AD 是公司内网的「用户名录」（Windows 域那套），OIDC 是互联网通用的「统一登录」（扫码／单点）。两者不冲突，都做成可插拔后端，企业用哪个都行。

## 4. agent 审计：命令日志还是会话录像（或都要）——todo.md L384 待拍板三条①

- **推荐决策**：暂缓，待批2（SSH 流量代理面）落地后再定；倾向命令日志优先（轻量可检索合规），会话录像延后。
- **理由**：
  1. 前提：当前 SSH 会话是「客户端本地直连目标机」，命令流不经 memex，无审计对象（todo L382）；必须先把流量改走 memex 代理面（批2）才有审计对象。
  2. 成本：命令日志轻量（文本＋检索）；录像需存储＋隐私（高风险）。
  3. 风险：录像存储成本高且涉隐私合规；命令日志覆盖面足够审计。
  4. 事实：会话审计深度＝仅接入留痕，无命令级日志、无会话录像（todo L375）。
- **立即执行动作**：记录决策，无代码动作（依赖批2）。✅ 已执行（记录决策，commit dfd764f）
- **不做／延后**：批2 未落地前不实现审计深度；录像作为后续可选。
- **教学**：命令日志＝记下「敲了什么命令」，轻便好查；会话录像＝录下整屏画面，又占地方又涉及隐私。所以先做命令日志。

## 5. 是否新增 group-server-* az 规则——todo.md L384 待拍板三条②

- **推荐决策**：新增 group-server-* az 规则（分批建议批1 口径：server:view/server:session 两动作起步，用现有群当组、某群=运维组即可收口）。
- **理由**：

  2. 成本：低——复用统一 az 引擎（authz.cpp default-deny），加两条规则＋审计。
  3. 风险：低——default-deny 口径下新增规则默认拒绝，显式授权才放行。
  4. 事实：多 agent 管理面无批量／分组／告警端点（todo L377），需先有分组面才有按组授权对象。
- **立即执行动作**：记录决策；规则实现作为后续（需与批1 分组面配套）。✅ 已执行（记录决策，commit dfd764f）
- **不做／延后**：不沿用「入群即授权＋群角色两档」的替代方案；独立角色层不引入（见下条）。
- **教学**：按组授权＝给整个运维组一次授权，不用一台一台配；az 规则＝访问控制条目，默认全拒，显式放行才通。

## 6. 用现有「群」当组还是独立角色层——todo.md L384 待拍板三条③

- **推荐决策**：用现有「群」当组，某群=运维组即可收口；不引入独立角色层。
- **理由**：
  1. 成本：现有群模型已有群成员＋群角色（群主／管理员），复用即零新增结构；独立角色层要新表／新迁移／新授权面。
  2. 收益：快；语义自然（运维组＝一个群）。
  3. 风险：独立角色层复杂度高，易与既有群权限打架。
  4. 事实：分批建议批1 明确「用现有群当组、某群=运维组即可收口」（todo L383）。
- **立即执行动作**：记录决策，无代码动作。✅ 已执行（记录决策，commit dfd764f）
- **不做／延后**：独立角色层不引入（除非后续按组授权需求证明不够用）。
- **教学**：一个「群」就是一组人，直接把运维人员拉进一个群就自然有了「运维组」，不用再造一套「角色」体系，省事。

## 7. 账号禁用控制——todo.md L519 待用户拍板三条①

- **推荐决策**：禁用账号即拒绝新登录＋踢其存量会话（fail-closed）。
- **理由**：
  1. 一致性：仓内已定 fail-closed 口径（LDAP 目录禁用踢下线，授权 default-deny）。
  2. 收益：禁用立即生效，不留已登录后门。
  3. 风险：低；需审计留痕（拒登＋踢出记日志）。
  4. 成本：小——登录口加禁用检查＋会话表吊销。
- **立即执行动作**：记录决策，无代码动作。✅ 已执行（记录决策，commit dfd764f）
- **不做／延后**：不做「禁用仅限新登录、存量不管」的宽松口径。
- **教学**：禁用账号＝这个人不能再进系统。如果只拦新登录、不踢已经在线的，那个人还能继续用，等于没禁用。所以既拦新登录也踢存量。

## 8. 停用设备是否踢存量会话——todo.md L519 待用户拍板三条②

- **推荐决策**：是——停用设备即踢其存量会话＋禁止其新会话。
- **理由**：
  1. 一致性：设备台账（T3.3）已有启停解绑；停用设备＝不再可信，fail-closed。
  2. 收益：停用即时生效。
  3. 风险：低（设备停用属管理动作）；需审计。
  4. 成本：小——会话表按设备吊销。
- **立即执行动作**：记录决策，无代码动作。✅ 已执行（记录决策，commit dfd764f）
- **不做／延后**：不做「停用仅限新会话」。
- **教学**：设备被停用（比如丢了／退役），它上面已经打开的会话也该一起关掉，否则设备还能收发。

## 9. files 令牌是否查设备闸——todo.md L519 待用户拍板三条③

- **推荐决策**：是——files 令牌也查设备闸（停用设备的令牌拒绝）。
- **理由**：
  1. 一致性：设备闸统一；否则停用设备仍可经文件面取数据（绕过会话闸）。
  2. 收益：补上旁路；安全边界完整。
  3. 风险：低；需与既有 files 令牌鉴权合并。
  4. 成本：小——文件令牌校验加设备状态检查。
- **立即执行动作**：记录决策，无代码动作。✅ 已执行（记录决策，commit dfd764f）
- **不做／延后**：不做「文件令牌免查设备闸」（留旁路）。
- **教学**：文件令牌＝取文件的钥匙。如果停用的设备还能用这把钥匙拿文件，那「停用」就白停了。所以文件面也要查设备状态。

## 10. 钉钉 DING 式对方侧强提醒（对端弹窗／角标）——todo.md L582 待用户拍板

- **推荐决策**：不采纳 DING 式对方侧强提醒。
- **理由**：
  1. 设计已代决：通知范围＝只给盯的人、对方无感、不升级成催促工具（todo L582 已代决）。
  2. DING 式恰恰是对端强提醒＝催促工具，与上述设计矛盾。
  3. 成本：对端新帧型＋开关，另立一单，且改变「对方无感」的既有已代决。
  4. 风险：打扰对方，与轻量自用跟进定位冲突。
- **立即执行动作**：记录决策，无代码动作。✅ 已执行（记录决策，commit dfd764f）
- **不做／延后**：不做 DING 式强提醒；维持「盯＝只提醒自己」。
- **教学**：「盯」本意是提醒自己「这条消息对方看了没」。如果还弹到对方那边去提醒对方，就变成催对方看，打扰人，也不是「盯」的本意了。所以不弹对端。

## 11. 盯「人」（对方上线即提醒）——todo.md L587 待用户拍板

- **推荐决策**：不立项；本单不做（依赖在线状态机制，属范围外）。
- **理由**：
  1. 前提：依赖在线状态机制；在线状态与「已读」是两套状态，语义不同。

  3. 风险：上线提醒易变打扰（对方频繁上下线）。
  4. 收益：有限（跟进价值低于已读盯）。
- **立即执行动作**：记录决策，无代码动作。✅ 已执行（记录决策，commit dfd764f）
- **不做／延后**：不做盯「人」；若后续要「对方上线提醒」，另立单。
- **教学**：盯「人」＝对方一上线就提醒你，这依赖「在线状态」。而且对方上线下线很频繁，会变成骚扰。先不做。
